# MAKCU mover (UDP): Raw 0x69/0x6A по сети

**Статус на 2026-10-10: транспорт работает, но 1000 Гц по UDP на прошивке 4094 не достижимы.**
Raw-путь по UDP доставляет каждый отчёт 1:1. Счётчики «отправлено = в FIFO = отдано в
USB-endpoint» сходятся, отказов 0, путь совпадает до отсчёта, в том числе при 25 % потерянных
датаграмм. Частота HID упирается в **250 Гц**. Ограничение на стороне платы: её UDP-обработчик
принимает ~583 датаграммы/с по одному кадру, а Raw тратит две датаграммы на отчёт (движение и
квитанция). Ниже цифры, которые это показывают, и всё, что пробовалось для обхода.

COM-вариант с 1000 Гц: [`../comport_way/README.md`](../comport_way/README.md). Этот стенд
устроен так же и подключает его общие заголовки.

## 1. Конвейер

```
 источник движения (Trajectory / ABCurves / накопитель) - как в comport_way
        │  каждые 1 мс: целый отчёт (dx,dy), часто (0,0)
        ▼
 runMotion (../comport_way/motion_engine.h): сетка QPC 1 мс, догон, перенос
        │  move(dx,dy): false = транспорт занят, дельта копится у вызывающего
        ▼
 RawUdpTransport (makcu_udp_transport.h)
        │  ведро темпа: <= 1 датаграмма на 2 мс (500/с) - ниже предела платы
        │  0x69 на ненулевую дельту, квитанция 0x6A - отдельной датаграммой
        │  датаграмма = 0x55 | nonce:8 | DE AD LEN CMD PAYLOAD (ровно один кадр)
        ▼  Ethernet -> свитч -> USB-хаб с Ethernet в host-порту MAKCU
 MAKCU fw 4094: UDP-обработчик ~583 датаграммы/с -> Raw FIFO -> один HID-отчёт на запрос
        ▼  USB, опрос 1 мс
 Windows: 250 отчётов/с, путь точный
```

Частота HID = частота принятых транспортом ненулевых `move()`, а их не больше
500 датаграмм/с / 2 = **250/с**. Остальное накопитель или рендерер сливает в следующий отчёт,
путь не теряется.

## 2. Что выяснено о UDP (шаг 0, всё замерено на этой плате)

Сеть: ПК `192.168.50.87` (кабель, свитч), плата `192.168.50.175:8080`, ping < 1 мс.

| Вопрос | Результат |
| --- | --- |
| Обёртка | **RAW**: `0x55` + nonce 8 байт + кадр MAK_API. Плата возвращает тот же nonce. Голый кадр (HOST без шифрования) остаётся без ответа. Шифрование не включено |
| DEVICE / FIRMWARE / `0x1F` | `0x03` (мышь + клавиатура) / **4094** / интерполяция 0 |
| `0x6A(id=0)` | schema 1, capacity 16. После перезагрузки платы `last_accepted_id` = 0 |
| Шаг 4: `0x69(1,0)` + `0x6A` | state 1 через 1.11 мс, квитанция через 3 мс: **state 2** (отдано в USB) |
| RTT | 1.05 мс p50, 1.15 мс p99 при темпе ≤ 500/с. Перестановок 0, дублей 0 |
| Несколько кадров в датаграмме | 2–4 кадра, пакет `MBAT` из SDK (BLE), запись без `DE AD`: **без ответа**, датаграмма отбрасывается целиком |
| Текст KM (`0x6B` = `'k'`) | работает: `m.version()` → `km.MAKCU`. Две команды в одном кадре (CRLF или `;`) дают `ERR`. Байт опкода в ответе - первая буква текста ответа |
| Безответные SET (`0x16`, `0x18`) | тоже занимают слот приёма: при 1000 датаграммах/с плата всё равно обрабатывает ~580 |
| Несколько сокетов-источников | 1, 2 или 4 порта: в сумме те же ~580/с |
| Потоки кнопок/ввода (`0x10`, `0x52`) | выключены, на приём не влияют |
| Что теряется при перегрузке | **запросы** (до обработки): опрос `0x6A(id, consume=0)` говорит «нет такого id». Потерянных ответов на принятые запросы не было |

## 4. Логика Raw по UDP (что отличается от COM)

Основа взята из `RawComTransport`: id строго растут, окно ≤ 12 записей (≤ свободно − 2), квитанция
не раньше 3 мс, перенос отказанных дельт, дочистка записей прошлых сессий, `finish()`. Отличия
под датаграммы:

- **Темп.** Ведро токенов: в среднем одна датаграмма на `--gap-us` (1800 мкс), ёмкость
  `--burst` (1). На сетке тиков 1 мс это ровно 2 мс. `move()` возвращает `false`, пока темп
  не позволяет, и не блокируется никогда.
- **Очерёдность.** Сначала новая дельта, квитанция - когда окно почти заполнено
  (живых ≥ окно − 2) или на пустых тиках. В установившемся режиме датаграммы чередуются:
  движение, квитанция.
- **Потерян `0x69`** (нет ответа 8 мс): опрос `0x6A(id, consume=0)`. Ответ «нет такого id»
  (255/5) значит, что запрос не дошёл: дельта уходит в перенос, движения не было. Если запись
  есть, потерялся только ответ, работа продолжается. Повторная отправка той же дельты под
  новым id без опроса запрещена контрактом, транспорт так и не делает.
- **Потеряна квитанция:** повтор `consume=1`. Если первая дошла, повтор получит 255/5 по
  известной записи: она считается отданной, растёт счётчик «неоднозначных». За все прогоны 0.
- **Перестановка и дубли:** ответ сопоставляется с запросом по nonce, ответ по уже закрытой
  записи идёт в «поздние ответы». В LAN не наблюдалось.

## 5. Сборка и запуск

```
build.bat
makcu_udp_mover.exe --check          связь + Raw + приём платы, курсор стоит (~3 с)
makcu_udp_mover.exe --netprobe       подробный замер приёма платы, курсор стоит (~10 с)
makcu_udp_mover.exe                  меню F-клавиш, формат rawmove
```

Выход - END (не убивать процесс: так возвращаются «Повышенная точность указателя» и
интерполяция, если её меняли).

### Меню

| Клавиша | Режим |
| --- | --- |
| F1 / F2 | 250 / 1000 тиков/с, 30 с, текущая фигура |
| F3 / F5 | ABCurves Renderer: рывки / круг, 30 с |
| F4 | накопитель, рывки, 30 с + таблица скорость → частота |
| F6 | перебор частот `--rates` (HID, путь, интервалы), мышь не трогать |
| F7 | формат: rawmove → move (0x18) → movenow (0x67) |
| F8 | 1000 тиков/с, линия 60 с (тест с рукой) |
| F9 | фигура: circle → eight → line → flicks |
| F10 | накопитель, лестница скоростей 0.05..8 отсч/мс по 2 с (24 с) + таблица |
| F11 | интерполяция `0x1F` по кругу 0 / AUTO / 25 / 50 / 100 (live, при выходе вернётся) |
| F12 | замер руки 15 с без инжекта |
| ESC / та же F-клавиша | стоп прогона |

### CLI

| Опция | Смысл |
| --- | --- |
| `--host IP`, `--udp-port N` | адрес платы (192.168.50.175:8080) |
| `--wire raw\|host` | обёртка; на 4094 отвечает только `raw` |
| `--gap-us N`, `--burst B` | темп датаграмм: средний интервал (1800) и ёмкость ведра (1) |
| `--tx rawmove\|move\|movenow` | формат; `move`/`movenow` идут через интерполятор |
| `--interp auto\|0..100` | интерполяция `0x1F` live (для 0x18/0x67) |
| `--compare A,B --rates N,..` | сравнение форматов (ramp, по 4 с на ячейку) |
| `--sweep`, `--run`, `--substep`, `--abc`, `--pattern`, `--speed`, `--size`, `--duration` | как у COM-стенда |

Вывод тот же, что у COM, плюс строка `udp ...`: датаграмм в секунду, сколько ждали ответа и
сколько пришло, RTT, ожидания темпа. В строке `raw 0x69` добавлены «потеряно запросов»,
«потерянных ответов», «опросов», «неоднозначных», «поздних ответов».

## 7. Что пробовалось для 1000 Гц и почему не вышло

| Идея | Итог |
| --- | --- |
| Несколько кадров в одной датаграмме (подряд, `MBAT`, несколько строк KM) | плата отбрасывает или отвечает `ERR` |
| Чаще датаграммы | всё, что сверх ~583/с, плата теряет до обработки |
| Несколько сокетов-источников | общий потолок |
| Безответные команды (`0x18`, `0x67`, SET) | стоят столько же, сколько запросы с ответом |
| Интерполятор (одна команда → несколько отчётов) | потолок ~626 Гц и потеря пути |
| Реже квитанции | нельзя: у платы 16 записей, квитанция освобождает ровно одну |
| Точнее темп (ведро ёмкостью 2) | +11 % (277 Гц) ценой потерь |

1000 Гц по UDP требуют изменений вне ПК. Варианты:
1. **COM** (`../comport_way`): 1000 Гц уже проверены.
2. **Прошивка**: пакетная отправка по UDP (несколько кадров в датаграмме) или квитанция
   диапазона id в Raw API. С пакетами по 2 движения + 2 квитанции на датаграмму раз в 2 мс
   хватило бы и текущих ~583 датаграмм/с. Это вопрос к MAKCU.
3. **Режим HOST / шифрованный UDP / Wi-Fi**: на этой плате не проверялись (HOST плата не
   принимает, ключа шифрования нет). Возможно, они устроены иначе, но переключение сети без
   COM-кабеля рискованно: можно потерять связь с платой.

## 8. Не проверено

- F3/F5 (ABCurves) по UDP: в меню есть, на железе не гонялись (ожидаемо: рендерер ~350 отчётов/с
  на рывках, транспорт сольёт их до ≤ 250).
- F12 и прогоны с рукой одновременно с инжектом.
- Долгие прогоны (10+ мин), перезагрузка платы посреди потока, Wi-Fi.
- Перестановка пакетов и дубли: логика есть (сопоставление по nonce), но в LAN они не возникали.
- Две программы с Raw API одновременно (общие id, как и на COM).
