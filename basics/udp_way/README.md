# MAKCU mover (UDP): Raw 0x69/0x6A по сети

> **Актуально на 2026-10-12: 1000 Гц по UDP достигнуты** на V4.097 (с 2026-10-11 официальная прошивка) командой batch `0x6C`.
> Эталонный транспорт: [`perfect-transport-udp/`](perfect-transport-udp/README.md). В mover это
> `--tx batch` (по умолчанию на прошивке ≥ 4097). Замеры и ответы инженеров MAKCU:
> [`MAKCU_RESPONSE_UDP.md`](MAKCU_RESPONSE_UDP.md). Ниже — история на прошивке 4094.

**Статус на 2026-10-10 (вечер): транспорт работает, Raw по UDP ~283 Гц, путь точный. 1000 Гц по
UDP на прошивке 4094 не найдены ни одним способом.**
Raw-путь по UDP доставляет каждый отчёт 1:1. Счётчики «отправлено = в FIFO = отдано в
USB-endpoint» сходятся, отказов 0, путь совпадает до отсчёта, в том числе при 25 % потерянных
датаграмм. С темпом «по ответам» (по умолчанию) частота HID **282–283 Гц** (с ведром было 250).
Ограничение на стороне платы. Её UDP-обработчик тратит **~1.72 мс на любой корректный кадр** и
принимает ровно один кадр на датаграмму, значит, не больше ~581 команды/с. Raw тратит две
датаграммы на отчёт (движение и квитанция), потолок ≈ 290 Гц. Сеть не теряет ничего: счётчик RX
сетевого интерфейса платы растёт на каждую отправленную датаграмму. Ниже цифры, модель приёма и
всё, что пробовалось для обхода (разделы 2, 7).

COM-вариант с 1000 Гц: [`../comport_way/README.md`](../comport_way/README.md). Этот стенд
устроен так же и подключает его общие заголовки.

## 1. Конвейер

```
 источник движения (Trajectory / ABCurves / накопитель) - как в comport_way
        │  каждые 1 мс: целый отчёт (dx,dy), часто (0,0)
        ▼
 runMotion (../comport_way/motion_engine.h): сетка QPC 1 мс, догон, перенос
        │  move(dx,dy): false = транспорт занят, дельта копится у вызывающего
        ▼
 RawUdpTransport (makcu_udp_transport.h)
        │  move(): дельта в перенос транспорта (темп по ответам)
        │  темп: в полёте одна датаграмма, следующая - сразу по ответу (поток приёма)
        │  0x69 с накопленной дельтой, квитанция 0x6A - отдельной датаграммой
        │  датаграмма = 0x55 | nonce:8 | DE AD LEN CMD PAYLOAD (ровно один кадр)
        ▼  Ethernet -> свитч -> USB-хаб с Ethernet в host-порту MAKCU
 MAKCU fw 4094: UDP-обработчик ~1.72 мс на кадр (~581/с) -> Raw FIFO -> один HID-отчёт на 0x69
        ▼  USB, опрос 1 мс
 Windows: ~283 отчёта/с, путь точный
```

Частота HID = число отправленных `0x69`, а их не больше половины датаграмм: ~566 датаграмм/с / 2
≈ **283/с** (с ведром `--pace bucket`: 500 / 2 = 250). Дельты тиков между отправками сливаются в
следующий отчёт, путь не теряется.

## 2. Что выяснено о UDP (шаг 0, всё замерено на этой плате)

Сеть: ПК `192.168.50.87` (кабель, свитч), плата `192.168.50.175:8080`, ping < 1 мс.

| Вопрос | Результат |
| --- | --- |
| Обёртка | **RAW**: `0x55` + nonce 8 байт + кадр MAK_API. Плата возвращает тот же nonce. Голый кадр (HOST без шифрования) остаётся без ответа. Шифрование не включено |
| DEVICE / FIRMWARE / `0x1F` | `0x03` (мышь + клавиатура) / **4094** / интерполяция 0 |
| `0x6A(id=0)` | schema 1, capacity 16. После перезагрузки платы `last_accepted_id` = 0 |
| Шаг 4: `0x69(1,0)` + `0x6A` | state 1 через 1.11 мс, квитанция через 3 мс: **state 2** (отдано в USB) |
| RTT | 1.05 мс p50, 1.15 мс p99 при темпе ≤ 500/с. Перестановок 0, дублей 0 |
| Несколько кадров в датаграмме | 2–4 кадра, пакет `MBAT` из SDK (BLE), запись без `DE AD`: **без ответа**, датаграмма отбрасывается целиком |
| Текст KM (`0x6B` = `'k'`) | работает: `m.version()` → `km.MAKCU`. Две команды в одном кадре (CRLF или `;`) дают `ERR`. Байт опкода в ответе - первая буква текста ответа |
| Безответные SET (`0x16`, `0x18`) | тоже занимают слот приёма: при 1000 датаграммах/с плата всё равно обрабатывает ~580 |
| Несколько сокетов-источников | 1, 2 или 4 порта: в сумме те же ~580/с |
| Потоки кнопок/ввода (`0x10`, `0x52`) | выключены, на приём не влияют |
| Что теряется при перегрузке | **запросы** (до обработки): опрос `0x6A(id, consume=0)` говорит «нет такого id». Потерянных ответов на принятые запросы не было |

остальных). Это гипотеза о внутреннем устройстве, цифры выше - факты.

### Важно: транспорт УМЕЕТ батч (один кадр на датаграмму - неверно как общий вывод)

Предел ~581/с - это про одиночные кадры с ответом. Встроенный тест производительности (`0x3F`)
принимает **несколько записей в одной датаграмме**: `0x3F 06 <count> <id u32 × count>`, count до 62.

| Проба | Результат |
| --- | --- |
| Батч из N записей в ОДНОЙ датаграмме увеличивает счётчик принятых ровно на N | `udp_perf.py`: дельта 1 / 10 / 62 |
| Батчи по 62 на пределе датаграмм | **34 643 записи/с** (589 датаграмм/с × 62, пик 35 109/с) = ~60× от 581 | `udp_perf_max.py` |
| `0x3F` - только счётчик (HID не выдаёт) | движение так не сделать |
| `0x69` строго 10 байт payload: 20/40/21 байт → `ff 01` (reason 1) | движение батчем не принимается | `udp_movebatch.py` |

Значит, узкое место для 1000 Гц - **не транспорт** (он тянет 34 000 записей/с), а то, что опкод
движения `0x69` берёт одну запись на датаграмму и требует квитанцию (ещё датаграмма).

### Маршрут без прошивки: WebSocket `/ws` (пока недоступен)

В образе прошивки 4076 (публичный, `app.makcu.com/makcu-fw`) у host-чипа есть HTTP + WebSocket
сервер (`GET /ws`, `101 Switching Protocols`). Toolkit гоняет сетевой тест именно через
`ws(s)://host/ws`, 4 сессии по 64 записи в кадре (~38k/с на демо). Если через `/ws` проходят
обычные команды - это путь к 1000 Гц мимо лимита датаграмм без правки прошивки. Но по Ethernet
плата его не отдаёт: ICMP и UDP 8080 работают, а **все 32 типовых TCP-порта - тайм-аут, ни одного
`refused`** (`tcp_ports.py`, `ws_probe.py`). TCP на этом интерфейсе «тёмный». Открывать - кнопкой
Geek (держать ~5 мин, по описанию открывает сетевой WebUI) или по другому интерфейсу.

Два маршрута к чистым 1000 Гц по UDP на 4094: (1) достучаться до `/ws` (без прошивки, но TCP надо
открыть); (2) вендор включает для `0x69` тот же батч, что уже работает для `0x3F` (крошечная
правка; 34 643 записи/с доказывают, что транспорт готов). Запрос: `MAKCU_REQUEST_UDP.md`.

Сетевые настройки платы (`0x3D`, формат из бандла Toolkit app.makcu.com, только чтение):
Ethernet mode Auto, выбран Device (DHCP-клиент; Host - прямое подключение, плата раздаёт адрес),
DHCP, порт UDP 8080, VLAN выкл., доступ к WebUI не запрещён флагом, интернет выкл.,
Wi-Fi/BLE/ESP-Hosted на этой плате нет. Режима «UDP-обёртка HOST/RAW» в настройках нет.
Карта опкодов из Toolkit: `0x08` = API_REBOOT (не слать!), `0x0C` = ключ AES и флаги шифрования
(ключ задаётся один раз навсегда), `0x3D` = Ethernet, `0x3E` = CONNECTION, `0x3F` = тест
производительности (пакует до 62–64 записей в один кадр, поле «вызывающий»: 1 Ethernet, 2 Wi-Fi, 3 COM, 4 BLE).

## 4. Логика Raw по UDP (что отличается от COM)

Основа взята из `RawComTransport`: id строго растут, окно ≤ 12 записей (≤ свободно − 2), квитанция
не раньше 3 мс, перенос отказанных дельт, дочистка записей прошлых сессий, `finish()`. Отличия
под датаграммы:

- **Темп по ответам (`--pace reply`, по умолчанию).** В полёте ровно одна датаграмма.
  Следующая уходит сразу по ответу на предыдущую: поток приёма отправляет её сам, между
  тиками. Если ответа нет `kReplyWaitUs` (3 мс), датаграмма всё равно уходит; потерю разберёт
  восстановление ниже. Ответ приходит через ~1.05 мс, то есть после окна выброса (~0.65 мс), но
  до конца цикла платы (1.72 мс). Новая датаграмма ждёт в «слоте», плата работает без простоя:
  ~566 датаграмм/с без потерь. `move()` всегда принимает дельту в перенос транспорта и
  отправляет её, если ответ на датаграмму в полёте уже пришёл. Иначе дельта уходит со
  следующей отправкой 0x69 из потока приёма. Если ответа нет, поток приёма просыпается раз в
  1 мс и досылает созревшие квитанции. Служебные запросы (`query`) ждут того же разрешения.
- **Ведро (`--pace bucket`, и всегда для 0x18/0x67 - у них нет ответа).** В среднем одна
  датаграмма на `--gap-us` (1800 мкс), ёмкость `--burst` (1). На сетке тиков 1 мс это ровно
  2 мс (500/с). `move()` возвращает `false`, пока темп не позволяет, и не блокируется никогда.
- **Очерёдность.** Сначала новая дельта, квитанция - когда окно почти заполнено
  (живых ≥ окно − 2) или запись созрела без новой дельты. В установившемся режиме датаграммы
  чередуются: движение, квитанция.
- **Потерян `0x69`** (нет ответа 8 мс): опрос `0x6A(id, consume=0)`. Ответ «нет такого id»
  (255/5) значит, что запрос не дошёл: дельта уходит в перенос, движения не было. Если запись
  есть, потерялся только ответ, работа продолжается. Повторная отправка той же дельты под
  новым id без опроса запрещена контрактом, транспорт так и не делает.
- **Потеряна квитанция:** повтор `consume=1`. Если первая дошла, повтор получит 255/5 по
  известной записи: она считается отданной, растёт счётчик «неоднозначных». За все прогоны 0.
- **Перестановка и дубли:** ответ сопоставляется с запросом по nonce, ответ по уже закрытой
  записи идёт в «поздние ответы». В LAN не наблюдалось.

## 5. Сборка и запуск

```
build.bat
makcu_udp_mover.exe --check          связь + Raw + приём платы, курсор стоит (~3 с)
```

### CLI

| Опция | Смысл |
| --- | --- |
| `--host IP`, `--udp-port N` | адрес платы (192.168.50.175:8080) |
| `--wire raw\|host` | обёртка; на 4094 отвечает только `raw` |
| `--pace reply\|bucket` | темп датаграмм rawmove: по ответам (по умолчанию, ~283 Гц) или ведро (250 Гц) |
| `--gap-us N`, `--burst B` | ведро: средний интервал (1800) и ёмкость (1); для 0x18/0x67 всегда |
| `--tx rawmove\|move\|movenow` | формат; `move`/`movenow` идут через интерполятор |
| `--interp auto\|0..100` | интерполяция `0x1F` live (для 0x18/0x67) |
| `--compare A,B --rates N,..` | сравнение форматов (ramp, по 4 с на ячейку) |
| `--sweep`, `--run`, `--substep`, `--abc`, `--pattern`, `--speed`, `--size`, `--duration` | как у COM-стенда |

Вывод тот же, что у COM, плюс строка `udp ...`: датаграмм в секунду, сколько ждали ответа и
сколько пришло, RTT, темп. Для темпа по ответам выводится, сколько датаграмм ушло сразу по ответу,
сколько по тайм-ауту и сколько раз дельта ждала в переносе; для ведра - ожидания темпа. В строке
`raw 0x69` добавлены «потеряно запросов», «потерянных ответов», «опросов», «неоднозначных»,
«поздних ответов».

## 7. Что пробовалось для 1000 Гц и почему не вышло

| Идея | Итог |
| --- | --- |
| Несколько кадров в одной датаграмме (один заголовок + кадры, `MBAT`, несколько строк KM) | плата отбрасывает или отвечает `ERR` |
| Несколько полных записей `55 nonce кадр` подряд (2–100), паддинг, выравнивание, IP-фрагментация | отбрасывается: принимается только длина 9 + 5 + LEN |
| Голый кадр (HOST) | отбрасывается бесплатно; режима HOST в настройках платы нет |
| Чаще датаграммы | всё, что сверх ~583/с, плата теряет до обработки (до этого всё доходит до её сетевого интерфейса) |
| Несколько сокетов-источников | общий потолок, окно выброса общее |
| Безответные команды (`0x18`, `0x67`, SET), текст KM `0x6B`, неизвестный опкод | стоят столько же (~1.7 мс), сколько запросы с ответом |
| Интерполятор (одна команда → несколько отчётов) | потолок ~626 Гц и потеря пути; старый метод 0x18 на 1000/с: 415 Гц, путь 0.14 |
| Реже квитанции | нельзя: у платы 16 записей, квитанция освобождает ровно одну (официальный контракт `raw-v4074.md`) |
| Точнее темп (ведро ёмкостью 2) | +11 % (277 Гц) ценой потерь |
| Темп по ответам (одна датаграмма в полёте) | **+13 % без потерь: 282–283 Гц**, теперь по умолчанию |
| WebUI/WebSocket по TCP (Toolkit гоняет тест в 4 сессиях) | TCP 80 не отвечает |
| Wi-Fi | на этой плате нет (флаги статуса `0x3D`; только через внешний донгл MAKNET) |
| Шифрованный UDP | не проверялся: нужен AES-ключ, задаётся один раз навсегда; решено не трогать |

1000 Гц по UDP требуют изменений вне ПК. Варианты:
1. **COM** (`../comport_way`): 1000 Гц уже проверены.
2. **Прошивка**: пакетная отправка по UDP (несколько кадров в датаграмме) или квитанция
   диапазона id в Raw API. С пакетами по 2 движения + 2 квитанции на датаграмму раз в 2 мс
   хватило бы и текущих ~583 датаграмм/с. Черновик запроса: `MAKCU_REQUEST_UDP.md`.
3. **Шифрованный UDP** (другой путь кода на плате): не проверялся, нужен ключ.

## 8. Не проверено

- Шифрованный UDP (AES-ключ задаётся один раз; решено пока не трогать).
- Почему 0x18 по UDP теряет путь при 500 командах/с, хотя все команды принимаются (на COM путь точный).
- Темп по ответам под движением руки (цикл платы растёт до ~2 мс) и долгие прогоны.
- F3/F5 (ABCurves) по UDP: в меню есть, на железе не гонялись (ожидаемо: рендерер ~350 отчётов/с
  на рывках, транспорт сольёт их до ≤ 283).
- F12 и прогоны с рукой одновременно с инжектом.
- Долгие прогоны (10+ мин), перезагрузка платы посреди потока, Wi-Fi.
- Перестановка пакетов и дубли: логика есть (сопоставление по nonce), но в LAN они не возникали.
- Две программы с Raw API одновременно (общие id, как и на COM).
