# perfect-transport-udp: замороженный транспорт MAKCU (UDP/Ethernet, batch 0x6C)

> ## ⚠ Обязательная настройка Windows для UDP: брандмауэр
>
> Плата присылает события кнопок `0x53` **с порта, равного порту программы, а не с 8080**. Если сеть с
> платой помечена как **Public** (у нас интерфейс `Ethernet` — Public), брандмауэр Windows **молча
> режет** эти пакеты для любой программы без разрешающего правила. Движение при этом работает, а кнопки
> держатся только на запасном опросе 5 мс (в `statsLine()`: «СОБЫТИЯ НЕ ДОХОДЯТ»).
>
> **Один раз: запустить `setup_firewall.bat`** из этой папки (двойной клик, права спросит UAC). Он создаёт
> или заменяет правило «MAKCU UDP events»: входящий UDP от локальной подсети для любой программы. IP платы
> знать не нужно, смена адреса правило не ломает. Цена: слать UDP программам на ПК может любое устройство
> этой подсети, а не только плата. Сузить можно параметрами:
>
> ```powershell
> .\setup_firewall.bat -Check                         # показать состояние, ничего не менять (тоже спросит UAC)
> .\setup_firewall.bat -InterfaceAlias Ethernet       # правило только для этого адаптера
> .\setup_firewall.bat -RemoteAddress 192.168.50.175  # только этот адрес, при смене IP запускать снова
> .\setup_firewall.bat -RemoteAddress Any             # любые адреса, если плата в другой подсети
> .\setup_firewall.bat -Remove                        # удалить правило
> ```
>
> Всё, включая `-Check`, скрипт выполняет в окне с правами администратора и печатает его вывод в исходном окне:
> на части систем без прав `Get-NetFirewallRule` правил не видит и возвращает пустой список, и проверка
> ложно говорила «правила нет». Ошибку чтения правил скрипт теперь выводит отдельно, а не выдаёт за «правила нет».
> Он же ищет **включённые запрещающие правила входящего UDP**: запрет сильнее разрешения, а Windows создаёт такой
> сама, если в окне «Разрешить доступ?» нажать «Отмена». Запрет для всех программ делает итог «рабочего правила нет»,
> запрет для одной программы печатается строкой `[i]`. Эту версию владелец отладил на ноутбуке друга 2026-11-17,
> там она сработала (подробностей прогона нет); на ПК стенда с правами администратора её ещё не запускали.
>
> `firewall_diag.bat` (рядом) - диагностика, только чтение, ничего не меняет: профили брандмауэра, сети и адреса,
> правила MAKCU, включённые запрещающие правила входящих, кто слушает UDP. Пишет `firewall_diag.txt` рядом с собой.
> Без прав администратора правил может не увидеть (см. выше), поэтому для честной картины запускать «от имени
> администратора». В файле есть адреса и список программ ПК: чужой файл не публиковать.
>
> Вместо правила можно пометить сеть как частную (у нас брандмауэр Private выключен):
> `Set-NetConnectionProfile -InterfaceAlias "Ethernet" -NetworkCategory Private`.
>
> **На этом ПК** пока действует правило 2026-10-12 только для `192.168.50.175`. Скрипт с правами
> администратора ещё не запускали: проверены `-Check`, `-WhatIf` и отказ при неверном адресе (правило цело).

Эталонный рабочий транспорт для сети, вынесенный в одну папку, по образцу
[`../../comport_way/perfect-transport-comport`](../../comport_way/perfect-transport-comport). Он **только
доставляет** целые отчёты `(dx, dy)` в MAKCU по UDP. Темп, нарезка траектории и квантование остаются на
стороне вызывающего кода. Это **единственный путь к ~1000 Гц по Ethernet**: Raw `0x69` по UDP упирается
в ~284 Гц, `0x18` в ~280 команд/с.

**Не править.** Если нужна другая версия, создайте новую папку. Источник: `../makcu_udp_transport.h`
(`RawUdpTransport`, `Format::Batch`) на 2026-10-12. Убраны форматы `0x69`/`0x18`/`0x67`, ведро токенов,
пробы приёма и обёртка HOST.

**Ревизия 2026-10-12 (2): кнопки мыши** (левая, правая, средняя, две боковые): события `0x53` плюс
страховочный опрос `0x55`. Логика движения не менялась. Изменилось окружение цикла: сокет без `connect()`
(события приходят с другого порта платы), поток приёма просыпается по high-resolution таймеру Windows,
а не по `select()`, поэтому опрос идёт по расписанию и без `timeBeginPeriod(1)` у вызывающего.

**Ревизия 2026-10-12 (3): инжект кнопок, блокировки, переподключение.** `press()`/`release()` всех пяти
кнопок (без тайминга: время удержания задаёт вызывающий), блокировки физического ввода (`setLock()`,
14 целей), сверка по снимку платы `0x56` и повтор потерянных команд, автопереподключение с
восстановлением, сброс состояния при `open()` и `close()`. Логика движения не менялась (самопроверка
движения после правки: 2000 из 2000, 99.7–99.8 % интервалов 1 мс).

**Ревизия 2026-10-30 (4): быстрые блокировки осей.** Направления движения уходят одной командой
`SET MOVE_MASK 0x16` (колесо — одной `0x17`) вместо серии `0x60`. Добавлен `setLocks({X, Y}, on)`:
несколько целей одним вызовом. Пауза после команды без ответа — 3 мс вместо 2. Замер с рукой на мыши:
физика перестаёт доходить до Windows через **1.3 мс в медиане, max 2.3** (`setLocks({X, Y})`). Было
7.7 мс, max 12.3: четыре `0x60` через 2 мс, и при опросе платы перед блокировкой каждая 4-я команда
терялась до исправления по снимку. Логика движения не менялась.

**Ревизия 2026-10-30 (5): курсор встаёт сразу и отсчёты живой мыши.**
- **Глубина очереди движения** `setMaxLag(n)`, по умолчанию 5 записей. Плата отдаёт в ПК одну запись
  на отчёт мыши, ровно столько, сколько мы шлём. Поэтому каждая заминка сети оставляла запись в
  очереди навсегда, и за 10 с движения хвост после последнего `move()` дорастал до **8 мс**: те самые
  3–4 кадра, на которые инжект «встаёт колом» позже. Теперь, если очередь доросла до 5 записей, новая
  дельта прибавляется к последней неотправленной записи. Путь точный, хвост **3.6 мс**, склеивается
  ~3 % отчётов (HID ~945 Гц, 97–98 % интервалов 1 мс). `setMaxLag(0)` возвращает прежнее поведение.
- **`stopMovement()`**: «встать колом». Неотправленные записи выбрасываются, доигрывает только то, что
  уже у платы. Курсор встаёт через **2.7–3.6 мс** (3 отчёта).
- **Отсчёты живой мыши** `setTracking(true)` / `physical()`. Пока нет инжекта движения, транспорт
  опрашивает позицию платы `GET 0x63` в свободные слоты (~475 раз/с) и копит разности. Сумма совпадает
  с Raw Input до отсчёта. Инжект в счёт не попадает: 8 всплесков по 1 с при неподвижной мыши — 0,0.

**Отличие от mover:** если очередь полна (7 записей), `move()` возвращает `false` и дельта остаётся у
вызывающего. Склейка по глубине очереди (ревизия 5) срабатывает раньше, на 5 записях.

## Адрес платы и автопоиск

Адрес у каждого свой: в режиме Device его выдаёт DHCP роутера, `192.168.50.175` — адрес только в нашей сети.
Порт 8080 — значение по умолчанию, но это настройка платы. Обнаружения по сети нет ни в `MAK_API.md`, ни в
контракте Raw, ни в SDK mak-suite (там `host` для UDP обязателен). Поэтому `makcu_udp_discover.h` находит
плату обходом. Транспорт не менялся: заголовок только возвращает адрес для `open()`. `example_line`,
`controls_test` и `track_test` используют его сами, `--host` у них по умолчанию `auto`.

| `host` в `resolveUdpHost` | Что происходит |
| --- | --- |
| `auto` | запомненный адрес, иначе обход. Несколько плат: выбирается запомненная по MAC, иначе ошибка со списком |
| MAC (`6c-1f-f7-c5-c6-68`, можно через `:`) | ищется именно эта плата: MAC не меняется, в отличие от IP |
| всё остальное (IP, имя) | возвращается как есть, сеть не трогается |

Как идёт поиск:
1. Запомненный адрес из `%LOCALAPPDATA%\MAKCU\udp_board.txt` (строка `IP MAC`). Если отвечает та же плата, обхода нет.
2. `GET DEVICE 0x02` на порт команд каждого адреса подсетей ПК, 3 прохода по 200 мс: первый может уйти на ARP.
   Платой считается только тот, кто вернул кадр обёртки RAW с нашим nonce и опкодом `0x02`.
3. У ответивших `FIRMWARE 0x04` и MAC из статуса `0x3D`, строго по одной команде.

Обход только читает. Брандмауэр ему не мешает: ответ идёт с того же адреса и порта, куда ушёл запрос.

**Проверка:** `find_makcu.exe`, рука не нужна, курсор не двигается. Верно: строка
`[+] 192.168.50.175:8080 | MAC 6c-1f-f7-c5-c6-68 | прошивка 4097 | маршрут мыши да`, код возврата 0.
Неверно: `[-] плат нет`, код 1. Тогда проверить кабель и `example_line.exe --host IP --check`. Ping здесь не
показатель: он может отвечать, пока порт 8080 молчит. В строке `обойдено:` видно, какие подсети проверялись.

**Замеры 2026-10-31, этот ПК, 3 подсети /24 плюс пропущенные 169.254.x.x и Tailscale /32:**

| Сценарий | Результат |
| --- | --- |
| `find_makcu.exe`, полный обход, настоящая плата | 609–610 мс, адрес, MAC и прошивка верные |
| `auto`, адрес запомнен | 0–15 мс (точность часов ~15 мс), подделка рядом не получила ни одного запроса |
| `auto`, запомненный адрес устарел | 1063–1110 мс, выбрана та же плата по MAC, файл обновлён |
| на запомненном адресе другая плата, в сети плата одна | 625 мс, найдена и запомнена она |
| файл испорчен | 625 мс, обычный обход |
| две платы, ничего не запомнено | ошибка со списком IP и MAC, файл не создан |
| `--host AA:BB:CC:00:00:0A` (регистр, двоеточия) | выбрана нужная плата |
| MAC, которого нет | ошибка `нет в сети` со списком ответивших |
| на порту 8080 чужой: неверный nonce, мусор, молчание | не приняты, найдена только настоящая плата |
| порт без плат (8081) | 609 мс, ошибка со списком подсетей |
| `example_line.exe --check` целиком, с поиском | 802 мс, с запомненным адресом 54 мс |

Вторая плата и чужие устройства здесь — подделки на Python на виртуальных адаптерах этого ПК. Поэтому обход
не исключает адрес самого ПК: ответить с него может только то, что говорит на протоколе платы.

**Ограничения:**
- обходится одна /24 вокруг адреса ПК, даже если подсеть шире. Плату дальше находить только через `--host IP`;
- 169.254.x.x пропускается: это адрес без DHCP, /16 не обойти;
- другой порт команд надо передать явно;
- `open()` запоминает IP. Если DHCP сменит адрес на ходу, транспорт будет ждать старый: закрыть его и снова
  пройти `resolveUdpHost` + `open()`.

**Не проверено:** настоящая вторая плата, режим Host (кабель напрямую в ПК, адрес раздаёт плата), отвечает ли
плата на широковещательный запрос, поиск на другом ПК. Запускать поиск, пока другая программа шлёт команды на
плату, не проверяли: у платы одна команда в полёте, запрос поиска может отнять у неё слот.

## Использование

```cpp
#include "makcu_udp_batch_transport.h"
#include "makcu_udp_discover.h"            // поиск платы, необязателен

makcu::UdpBatchTransport tx;
std::string host = "auto", err;            // или готовый IP: тогда поиска нет
if (!makcu::resolveUdpHost(host, 8080, err) || !tx.open(host, 8080, err)) { /* err - причина */ }

// поток тайминга, каждый тик (обычно 1 мс):
pendX += dx; pendY += dy;                      // ваш целый отчёт за тик
if ((pendX || pendY) && tx.move(int16_t(pendX), int16_t(pendY))) pendX = pendY = 0;
// move() == false - дельта остаётся в pend и уйдёт следующим тиком

tx.finish();   // конец движения: дослать очередь, дождаться квитанции, освободить записи (до 300 мс)
tx.close();
```

Кнопки (из любого потока, не блокируют):

```cpp
if (tx.buttonDown(makcu::MouseButton::Side2)) { /* боковая 2 зажата сейчас */ }
uint8_t mask = tx.buttons();                    // bit0 левая .. bit4 side2
uint32_t n = tx.pressCount(makcu::MouseButton::Left);  // нажатий с open(): разность = клики между чтениями
tx.setButtonPollMs(50);                         // страховочный опрос (по умолчанию 50 мс, 0 - выключить)
```

Инжект кнопок и блокировки (из любого потока, не блокируют):

```cpp
tx.press(makcu::MouseButton::Left);             // нажать; удержание - на вашей стороне
tx.release(makcu::MouseButton::Left);           // отпустить
tx.setLock(makcu::LockTarget::Side2, true);     // side2 больше не доходит до игры, но buttons() её видит
tx.setLock(makcu::LockTarget::X, true);         // ось X физической мыши (оба направления)
tx.setLocks({makcu::LockTarget::X, makcu::LockTarget::Y}, true);  // обе оси ОДНОЙ командой: ~2 мс
tx.unlockAll();                                 // снять все блокировки
if (!tx.connected()) { /* связь пропала, транспорт переподключается сам */ }
```

Чувствительность физической мыши (из любого потока, не блокирует; добавлено 2026-11-12):

```cpp
tx.setSensitivity(50);                          // рука двигает курсор вдвое меньше, как 400 DPI вместо 800
tx.setSensitivity(100);                         // как было (по умолчанию)
int pct = tx.sensitivity();                     // что задано сейчас
```

Встать колом и отсчёты живой мыши (ревизия 5):

```cpp
tx.stopMovement();                              // инжект: курсор встаёт через ~3 мс, неотправленное выброшено
tx.setTracking(true);                           // опрос позиции платы, пока нет инжекта (km.screen 32767)
auto a = tx.physical();                         // a.x, a.y - отсчёты физической мыши; a.live - отрезок идёт
// ... мышь двигают ...
auto b = tx.physical();                         // b.x - a.x, b.y - a.y: движение руки между чтениями
tx.setTracking(false);                          // km.screen как было
```

## Контракт

| | |
| --- | --- |
| `open(host, port, err)` | UDP `host:port` (8080), обёртка RAW. `DEVICE 0x02` (маршрут мыши), `FIRMWARE 0x04` ≥ 4097, Raw-метаданные `0x6A(id=0)`, дочистка записей прошлых сессий. `false` + причина: плата не в сети, нет мыши, прошивка без `0x6C` |
| `move(dx, dy)` | **один принятый вызов = одна запись = один HID-отчёт**; если очередь движения доросла до `maxLag` (5), дельта прибавляется к последней неотправленной записи (путь точный, `stats().merged`). Никогда не блокируется на сети. `false` = очередь из 7 записей полна или транспорт неисправен: дельту хранит вызывающий |
| `setMaxLag(n)` / `maxLag()` | глубина очереди движения, записей; по умолчанию 5, `0` — не ограничивать (как до ревизии 5). Отставание курсора от `move()` и хвост после остановки ≈ `n` мс. Замер: без предела за 10 с хвост дорастает до 8 мс, с 5 — 3.6 мс, склеено ~3 % |
| `stopMovement(&dx, &dy)` | «встать колом»: записи, ещё не отправленные плате, выброшены (их сумма — в `dx`/`dy`); пакет в полёте и очередь платы доиграют (отозвать нельзя). Курсор встаёт через 2.7–3.6 мс |
| `setTracking(on)` / `tracking()` / `physical()` | отсчёты живой мыши по позиции платы `GET 0x63`. Опрос в свободные слоты цикла, **только пока нет инжекта движения**; под полной блокировкой осей встаёт через 5 мс после подтверждения (позиция там не меняется). `physical()`: `x`, `y` — накопленные отсчёты с `setTracking(true)`, `samples`, `sampleQpc`, `live`. Первый `move()` закрывает отрезок, следующий начинается через ~8 мс после последнего `move()` (плата отдаёт очередь). Опрос занимает единственный слот: `move()`/`press()`/`setLocks()` ждут ответа на него (до ~2 мс). На время слежения `km.screen` = 32767×32767 (запас ±16k отсчётов, перецентровка, когда мышь стоит), потом прежний. `setTracking(true)` блокирует до ~0.3 с |
| `move(0, 0)` / `service()` | на мышь ничего не уходит. Отправить пакет, если предыдущий уже квитирован (обычно это делает поток приёма) |
| `finish(ms = 300)` | дослать очередь, дождаться квитанции, освободить хвост записей на плате. `true` = всё отдано, плата чистая |
| `stats()` / `statsLine()` | счётчики, можно вызывать из любого потока |
| `buttons()` / `buttonDown(b)` | маска физических кнопок (bit0 левая, 1 правая, 2 средняя, 3 side1, 4 side2). Любой поток, не блокируют. Обновляется событием `0x53` (~1 мс), страховка — опрос `0x55` |
| `pressCount(b)` | нажатий (переходов 0 → 1) с `open()`. Клик не теряется, даже если `buttons()` читают редко. Кнопка, зажатая уже при `open()`, нажатием не считается. Если события режет брандмауэр, клик короче 5 мс может пройти мимо опроса |
| `setButtonPollMs(ms)` | интервал страховочного опроса `0x55`, по умолчанию 50 мс; `0` выключает опрос совсем. Без событий опрос сам идёт не реже 5 мс |
| `press(b)` / `release(b)` / `setButtonState(b, down)` / `releaseAllButtons()` | инжект кнопки (`SET 0x11…0x15`). Уходит следующей командой цикла, **раньше движения** из очереди: ждёт только команду, которая уже в полёте. Замер: от `press()` до события в Windows 1.3–1.55 мс в среднем, max 1.87 мс. Инжект складывается с физикой (ИЛИ): отпускание физической кнопки не отменяет программное нажатие |
| `injectedButtons()` / `injectedButtonsOnBoard()` | запрошенная маска инжектированных кнопок / что на плате по последнему снимку (до 250 мс назад) |
| `setSensitivity(pct)` / `sensitivity()` | доля движения **физической** мыши, которая доходит до ПК, 0…100 %; 100 — выключено. Любой поток, не блокирует, менять можно на ходу. Инжект не уменьшается, но идёт более крупными шагами (склеек 25 % против 6–7 %). Окна маски от 6 мс: при 50 % — 83 порции в с. Замер: 75 / 50 / 33 / 25 / 10 % дали 75.6 / 49.8 / 33.6 / 24.4 / 10.0 %. См. «Чувствительность физической мыши» |
| `setLock(t, on)` / `setLocks({t…}, on)` / `unlockAll()` / `locked(t)` / `locks()` / `locksOnBoard()` | блокировка физического ввода: 5 кнопок, оси X/Y и колесо целиком или по направлению. Направления движения — одной `SET 0x16`, колесо — одной `0x17`, кнопки — `SET 0x60`. Заблокированное не доходит до ПК от физической мыши; инжект проходит; `buttons()` видит физику и у заблокированной кнопки. **Обе оси — через `setLocks({X, Y}, on)`**: одна команда, физика встаёт через ~1.3 мс (max 2.3). Два вызова `setLock` подряд — две команды через 3 мс (4.3 мс, max 5) |
| `connected()` | связь с платой есть. `false` — идёт переподключение, `move()` возвращает `false` |
| `open()` | дополнительно: включает поток событий, приводит плату в чистое состояние — снимает инжектированные кнопки и блокировки, оставшиеся от упавшей программы |
| `close()` | отпускает все инжектированные кнопки, снимает все блокировки (с подтверждением снимком), возвращает поток `INPUT_STREAM mouse` в состояние до `open()` |
| потоки | `move`/`service`/`finish` вызываются **из одного потока**. Внутри свой поток приёма: он же шлёт следующий пакет сразу по квитанции |
| потери | непринятые платой записи (нет места) транспорт возвращает в очередь сам. Нет квитанции 30 мс: опрос `last_accepted_id`, принятое засчитывается, остальное в очередь. Путь не теряется и не дублируется |

Чего транспорт **не** делает: не держит часы и темп, не нарезает траекторию, не копит дробные дельты и не
добавляет шум. Частота HID равна частоте ненулевых принятых `move()` и не выше опроса USB клонированной мыши.

## Как это работает

Каждая UDP-команда идёт на второй чип MAKCU по внутреннему каналу, который везёт одну команду за раз.
Датаграмма, пришедшая во время передачи, **молча выбрасывается** (подтверждено инженерами MAKCU). Поэтому:

- в полёте **один пакет**; следующий уходит из потока приёма сразу по квитанции (closed loop);
- в пакете **до 7 записей**, по одной на тик `move()`. Квитанция сообщает не больше 7 терминальных строк,
  поэтому 16 записей дают ту же скорость: лишние возвращаются с `reason 3` («нет места»);
- поле `X` следующего пакета = старший терминальный id из квитанций (флаг `bit0`): плата освобождает
  записи без отдельных квитанций `0x6A`.

При RTT ~1.9 мс за оборот накапливается ~2 записи, так что пакет в среднем несёт 1.9 записи, а
задержка от `move()` до отправки не больше одного оборота.

## Кнопки мыши

`open()` включает поток событий `INPUT_STREAM mouse` (`0x52 01 01`, без ответа), затем читает стартовую
маску `GET PHYS_BUTTONS 0x55`. Дальше маску держат два источника:

- **события `0x53`**: `55 <nonce> DE AD 03 00 53 01 <id> <0|1>` приходят сразу по нажатию. Внутри стоит
  nonce одной из наших прошлых команд, поэтому транспорт разбирает их по опкоду **до** сопоставления
  ответов по nonce, иначе событие можно принять за квитанцию пакета;
- **страховочный опрос `0x55`** раз в 50 мс в том же замкнутом цикле, что и движение. Он исправляет маску,
  если событие потерялось (UDP не повторяет пакеты). Если события не приходят вообще, а опрос уже дважды
  нашёл изменения, транспорт сам учащает опрос до 5 мс. В `statsLine()` тогда стоит
  «СОБЫТИЯ НЕ ДОХОДЯТ (брандмауэр?)».

`close()` возвращает поток `0x52` в то состояние, в котором он был до `open()`.

**Почему сокет без `connect()`.** Ответы на команды плата шлёт с порта 8080, а события — с порта, номер
которого равен порту клиента (проверено: `from 192.168.50.175:54444` на наш `:54444`). Подключённый сокет
принимает только `плата:8080` и события выбрасывает. Транспорт принимает любые датаграммы с IP платы.

**Брандмауэр Windows.** Если сеть с платой помечена как **Public** и брандмауэр Public включён, события
«с чужого порта» он режет для программы без разрешающего правила. Ответы на команды проходят, поэтому
движение и опрос работают, а события нет. Тогда работает страховочный опрос 5 мс (задержка ≤ ~6 мс, клик
короче 5 мс можно пропустить). Чтобы события доходили, нужно одно из двух (права администратора):

```powershell
# правило для пакетов из локальной подсети, для любой программы (параметры - в начале этого файла)
.\setup_firewall.bat
# или пометить сеть с платой как частную (если брандмауэр Private выключен или там есть правило)
Set-NetConnectionProfile -InterfaceAlias "Ethernet" -NetworkCategory Private
```

Порт программы случаен, поэтому сузить правило по порту нельзя. Python для проверки не годится:
у `anaconda python.exe` своё разрешающее правило, события он видит и без нашего.

Цена для движения: опрос — такая же команда в полёте, как пакет `0x6C`, только ответ быстрее (RTT ~1 мс).
При опросе 5 мс пакеты становятся плотнее (~3 записи вместо ~1.9), а 1000 Гц сохраняются: 2000 из 2000,
99.3–99.9 % интервалов 1 мс.

### Ловушки, на которых ломается интеграция

- **Бинарные `0x11…0x15` (LEFT…SIDE2) физическую кнопку не видят.** Они возвращают только
  инжектированное состояние («софт держит кнопку»), поэтому физическое нажатие там всегда 0. Физику
  дают `0x55 PHYS_BUTTONS`, события `0x53` и текстовые `km.left()…km.side2()` (0 нет / 1 физ. / 2 инж. / 3 обе).
- **Старый поток `0x10 BUTTONS` не нужен.** В режимах 1/2 он вставляет в COM текст `km.<маска>\r\n` между
  бинарными кадрами (его включает SDK mak-suite при connect). Транспорт его не трогает и не разбирает.
- **Каждое включение потока `0x52` начинается с «всё отпущено».** Зажатая кнопка придёт событием только
  со следующим отчётом мыши, поэтому стартовую маску транспорт читает через `0x55` уже после включения.
- **По UDP события `0x53` приходят, но с «чужого» порта.** Плата шлёт их на порт клиента, а исходный порт
  ставит равным порту клиента, не 8080. Сокет с `connect()` такие датаграммы молча выбрасывает (поэтому
  первая проверка показала «0 событий»), а брандмауэр Windows на сети Public режет их для программы без
  разрешающего правила. UDP-транспорт сокет не подключает и страхуется опросом `0x55`.

## Чувствительность физической мыши

`setSensitivity(pct)` уменьшает движение руки до заданной доли: 50 % — как если бы DPI мыши стал вдвое ниже. 0…100, 100 — выключено
(по умолчанию), 0 — рука курсор не двигает. Любой поток, не блокирует, менять можно на ходу, `close()` возвращает 100. Инжект
`move()` не уменьшается. Вызов тот же, что в COM-эталоне, **по UDP он грубее и инжект рядом с ним идёт хуже**.

**Как сделано.** У платы нет масштаба физического движения: маска направлений `SET 0x16` либо пропускает отчёт мыши целиком, либо
выбрасывает. Цикл эталона ставит и снимает маску всех четырёх направлений окнами в целое число мс, не короче 6 мс
(`kSensMinWindowMs`; по COM 2 мс). Причина: после команды без ответа канал 3 мс занят (`kNoReplyGapUs`), а пакетам движения тоже
нужно место; стенд `--assist` показал, что при периоде 12 мс инжект рядом идёт, а при 8 мс встаёт. Короткое окно всегда 6 мс,
длинное = `6 × доля / (1 − доля)` или обратное, дробная часть переносится на следующий период, так что среднее равно заданному:

| Задано | Окно пропуска | Окно маски | Порций движения в с |
| --- | --- | --- | --- |
| 75 % | 18 мс | 6 мс | 42 |
| 50 % | 6 мс | 6 мс | 83 |
| 25 % | 6 мс | 18 мс | 42 |
| 10 % | 6 мс | 54 мс | 17 |

Расписание окон ведёт `sensLocked()` в `pumpLocked()`, саму команду отправляет `sendControlLocked()`, когда канал свободен;
переключение уходит **без снимка-проверки** (маску сверяет пульс-снимок раз в 250 мс).

**Замер 2026-11-12** (V4.122, `track_test.exe --sens 1 --seg 3000 --duty 100,75,50,33,25,10`, рука водит кругами, отрезки по 3 с,
доля = сообщения Raw Input с движением / все сообщения):

| Задано | Фактически | Переключений маски в с | Интервалов ~1 мс | Max пауза |
| --- | --- | --- | --- | --- |
| 100 % | 100.0 % | 0 | 96.6 % | 3.0 мс |
| 75 % | **75.6 %** | 83 | 96.7 % | 2.2 мс |
| 50 % | **49.8 %** | 166 | 93.6 % | 44.0 мс |
| 33 % | **33.6 %** | 110 | 95.6 % | 2.7 мс |
| 25 % | **24.4 %** | 83 | 95.5 % | 3.1 мс |
| 10 % | **10.0 %** | 33 | 98.0 % | 3.0 мс |

1425 переключений, 92 снимка, `исправлено 0`, после возврата к 100 % маски на плате нет.

**Инжект под чувствительностью 50 % — хуже, чем без неё** (мышь не трогали; `--inject 3 --dur 300,1000`; базовая строка из
прогона `--inject 3 --dur 300,1000,3000` за несколько минут до этого):

| Прогон | Записи = сообщения | Путь | Хвост после последнего `move()` | Интервалов 1 мс | Склеено `move()` | Max дыра, max шаг |
| --- | --- | --- | --- | --- | --- | --- |
| без чувствительности, 6 кругов | 6 из 6 | точный | 3.5–6.6 мс | 94.2–94.8 % | 6–7 % | 3–5 мс, 5–8 отсчётов |
| чувствительность 50 %, 4 круга | 4 из 4 | точный | 3.3–8.3 мс | 83.0–85.3 % | 25 % | 6–9 мс, 10–14 отсчётов |

Путь остаётся точным, но каждая команда маски отнимает у движения 3 мс: инжект идёт более крупными и редкими шагами.

**Оба прогона оборваны зависанием платы** (`обрывов 1`, дальше `плата не найдена на порту 8080`):
- без чувствительности — на первом круге 3 с, примерно на 2.3-й секунде;
- с чувствительностью 50 % — на пятом круге (1 с), примерно на 0.78-й секунде; в момент обрыва на плате стояла маска `07E0`
  (X и Y закрыты), транспорт снять её не смог: связи не было.

Первое зависание было без маски, поэтому приписать его чувствительности нельзя; подробно — `HANDOFF_UDP_TRACKING_HANG.md`. Но
следствие для встраивания есть: **если плата зависнет в окне маски, рука останется заблокированной до перезагрузки платы.**

**Что надо знать при встраивании:**
- движение руки приходит порциями (таблица выше), под маской отчёты идут каждую мс, но пустые;
- блокировки `setLock()` и кнопки идут со снимком, как раньше, и складываются с маской чувствительности;
- `locksOnBoard()` показывает то, что стоит на плате, вместе с маской чувствительности; `locks()` — только запрошенное;
- `physical()` под маской движение руки не считает;
- активного ожидания нет (расписание идёт по тику приёма 1 мс), поэтому окно может сдвинуться на ~1 мс; среднее от этого не уходит.

**Не проверено:** долгая работа; переподключение с включённой чувствительностью; `controls_test` и `example_line` с движением на
этой сборке; значения 1–9 % и 76–99 %; пауза 44 мс на отрезке 50 % (рука или дыра, не выяснено).

## Инжект кнопок и блокировки

Команды `SET 0x11…0x15` (кнопки), `SET 0x16`/`0x17` (маски движения и колеса) и `SET 0x60`
(блокировки) у платы **без ответа**. Это значит:

- **пауза 3 мс после каждой такой команды.** Замер 2026-10-12: следующая команда раньше чем через
  ~1 мс молча теряется (идёт передача на второй чип), с 1.5 мс проходят 40 из 40, но это при
  неподвижной мыши. Замер 2026-10-30: если перед серией шёл опрос платы, а рука двигала мышь, то
  при паузе 2 мс одна из четырёх `0x60` терялась в 33 попытках из 46. При паузе 3 и 4 мс потерь
  0 из 46, одна `0x16` — 0 из 45. Без опроса перед серией потерь нет и при 2 мс (620 из 620);
- **сверка снимком `GET 0x56 INJECT_SNAPSHOT`** (40 байт: `[0]` инжектированные кнопки, `[1..2]` маска
  блокировок, бит = номер цели) сразу после команд и раз в 250 мс. Если на плате не то, что
  отправлено (потерялась датаграмма, плату перезагрузили, вмешалась другая программа), транспорт
  отправляет разницу заново (`stats().repairs`).

Транспорт хранит **запрошенное** состояние (маски кнопок и блокировок), а не очередь команд: несколько
быстрых `press`/`release` подряд схлопываются до итогового состояния. Если нужно гарантированное
нажатие короче оборота цикла, удерживайте кнопку хотя бы несколько миллисекунд.

**Оси в блокировках.** У платы по каждой оси два бита, «+» и «−». Бит оси целиком (`X`, `Y`, `Wheel`)
плата выставляет сама, когда заблокированы оба направления. Замер: «+X, затем −X» → `{X,+X,−X}`;
«X, затем снять +X» → `{−X}`. Поэтому `setLock(X, on)` ставит или снимает оба направления, а
`setLock(XPos, false)` при заблокированной оси оставляет только −X.

**Блокировка движения одной командой.** `SET MOVE_MASK 0x16 left right down up` — то же состояние,
что и цели `0x60` («a lock is the same state as the matching mask»). Проверено снимком: left → −X
(бит 7), right → +X (6), down → +Y (9), up → −Y (10), все четыре → `07E0` с битами осей целиком.
`0x16 0000` снимает и то, что ставилось через `0x60`. Колесо: `0x17 down up` → биты 13, 12. Транспорт
отправляет все четыре направления одной `0x16`, как только меняется любое из них.

Задержка блокировки, `probes/track_test.exe --reflock 20` (2026-10-30, рука водит кругами; от вызова
до последнего физического отсчёта в Windows Raw Input):

| Как | Медиана | Max | Утечка (отсчёты) |
| --- | --- | --- | --- |
| ревизия 3: `setLock(X)` + `setLock(Y)` = четыре `0x60` через 2 мс | 7.65 мс | 12.3 мс | 3–23 |
| ревизия 4: `setLock(X)` + `setLock(Y)` = две `0x16` через 3 мс | 4.3 мс | 5.0 мс | 1–14 |
| ревизия 4: `setLocks({X, Y})` = одна `0x16` | **1.3 мс** | **2.3 мс** | 0–11 |

Меньше ~1–2 мс не получится: команда идёт на второй чип, плюс ближайший отчёт мыши. Утёкшие отсчёты
Windows получил, и позиция платы `0x63` их тоже видит. Движение под блокировкой позиция платы не
считает: 0 отсчётов за 400 мс при руке на мыши.

## Переподключение

Опросы и снимки работают как пульс: если от платы нет ни одной датаграммы 750 мс, связь считается
потерянной. Тогда:

- `connected()` и `healthy()` дают `false`, `move()` возвращает `false`. Записи движения, не дошедшие до
  платы, сбрасываются (`stats().droppedRecords`): к моменту восстановления они устарели. Пример и тест
  в это время тоже сбрасывают накопленную дельту, чтобы не было рывка;
- сторожевой поток раз в 250 мс пробует рукопожатие заново. После успеха он продолжает id записей,
  включает поток событий, перечитывает кнопки и по снимку дошлёт запрошенные блокировки и кнопки
  (после перезагрузки платы они пропадают);
- замер: кабель хаба выдернут на несколько секунд → обрыв замечен, через 14.3 с (линк сетевой карты +
  DHCP платы) связь восстановлена сама, блокировка на месте, движение продолжилось.

**Ограничение.** Если в момент `close()` связи нет или программа упала, не дойдя до `close()`, зажатые
программой кнопки и блокировки **остаются на плате**: прошивка не отпускает их сама. Их снимет
следующий `open()` этого транспорта (он приводит плату в чистое состояние) или перезагрузка платы.
Ставьте обработчик Ctrl+C и закрытия консоли, который вызывает `close()`.

## Требования

- Прошивка с batch `0x6C`: **V4.097** и новее. С 2026-10-11 V4.097 — официальная прошивка MAKCU;
  V4.095 и старее `0x6C` не умеют, на них `open()` вернёт ошибку.
- Сеть MAKCU: USB-Ethernet в USB3-порту платы. Проверено на хабе **UGREEN 60554** (Genesys Logic
  `05E3:0610` + гигабитный NIC **ASIX AX88179 `0B95:1790`**), мышь в том же хабе, PC → свитч → RJ45 хаба.
  Внешнее питание хаба по USB-C на результат не влияет.
- Мышь в host-порту MAKCU опрашивается на 1000 Гц: плата копирует её интервал опроса.
- Сам транспорт «Повышенную точность указателя» не трогает. Для точного пути в Windows её выключает
  вызывающий.

## Перепроверка 2026-10-30 и известные ограничения

После COM-ревизии 5 эталон замерен снова, код не менялся (`probes/track_test.exe`, общий стенд `../../track_bench.h`).

| Прогон | Результат |

- **Рука на мыши.** Отчёты физики занимают слоты HID, поэтому хвост 6–9 мс, а не 3.6. Это 3–4 кадра при 400–500 кадрах/с. Предел помогает
  лишь частично. Значения меньше 5 с рукой не мерили, без руки 2–3 сильно портят интервалы.
- **Клики и блокировки на ходу.** Каждая команда без ответа даёт паузу 3 мс и снимок, в потоке движения видны паузы 6–10 мс.
- **`km.screen` не проверяется.** `SET 0x64` без ответа: если датаграмма потеряна, `setTracking(true)` вернёт успех при старом размере, а
  после выключения может остаться 32767×32767. В COM-эталоне проверка есть.
- **Зависание USB3 на 4097.** При долгом движении пропадают мышь и сеть, помогает только переподключение платы (2026-10-12, 3-я минута;
  2026-10-30, ~65-я секунда). `--soak` и `--reconnect` со слежением на ревизии 5 поэтому не пройдены.
- **Причина зависания (2026-11-13, V4.122): темп команд.** Эталон шлёт следующую команду сразу по ответу: пакеты `0x6C` при инжекте
  (~500/с по 2 записи) и опрос `0x63` при слежении (~510/с). Это предел платы (~530/с). Под чистым инжектом эталона плата умерла
  на 33-й с, под одним слежением на 99-й. Голая проба `probes/udp_soak.exe` без эталона: 510/с и без паузы - обрывы на 11-190 с,
  команда любая; 350/с - один обрыв на 217 с; **250/с - 30 мин без единой потери**. Перед обрывом 1-3 с единичных потерь ответов.
  **Эталон в этом виде на V4.122 долго не живёт.** Починка (не сделана): общий нижний предел периода команд, кандидат 4 мс
  (250/с). 1000 Гц инжекта при этом остаются: пакеты по ~4 записи вместо 2 (на 4097: 139 пакетов/с по 7 записей = 970 отчётов/с),
  цена - задержка, оценка +2-3 мс к хвосту. Подробно: `HANDOFF_UDP_TRACKING_HANG.md`, «Серия 2026-11-13».

## Протокол на проводе (для справки)

Датаграмма: `0x55 | nonce u64 | DE AD | LEN u16 | CMD u8 | PAYLOAD`. Ответ несёт тот же nonce, payload
с байта 14. Одна команда на датаграмму.

- `0x6C BATCH` (V4.097+): `01 | flags | N | 00 | X u32 | N × [id u32 | x i16 | y i16 | dt u16]`, длина
  ровно `8 + 10N`. `flags bit0`: освободить терминальные записи с `id ≤ X`. `X` не больше старшего
  терминального id, уже сообщённого квитанцией, иначе `255 / reason 1` без последствий.
- Квитанция: `[0]=1 [1]=0 все / 1 частично / 255 отклонено [2]=N [3]=принято [4]=первый отказ
  [5]=причина [6]=освобождено [7]=свободно [8]=K строк (≤ 7) [9]=more [10]=в очереди [11]=0
  [12..15]=last_id`, затем `K × (id u32 | state u8 | reason u8)` по возрастанию id. Записи принимаются
  подряд с первой; `state 2` = отдано в USB-endpoint, `3` = отказ.
- `0x6A RAW_ACK`: `id = 0` → метаданные `schema, last_accepted_id, free_records, capacity (16)`;
  `(id, consume = 1)` → освободить терминальную запись (дочистка хвоста в `open()`/`finish()`).
- ID строго растут в пределах загрузки платы. Ёмкость платы 16 записей.
- `0x55 PHYS_BUTTONS` (V4.036+): пустой запрос → `mask:u8` физических кнопок. Ответ ~1 мс.
- `SET 0x11…0x15` (LEFT…SIDE2): `state:u8` (1 нажать, 0 отпустить), **без ответа**. `GET` тех же опкодов
  отдаёт только инжектированное состояние, не физику.
- `SET LOCK 0x60`: `target:u8 state:u8`, **без ответа**; `GET LOCK 0x60 target:u8` → `state:u8`. Цели:
  0 left, 1 right, 2 middle, 3 side1, 4 side2, 5 X, 6 +X, 7 −X, 8 Y, 9 +Y, 10 −Y, 11 wheel, 12 wheel+,
  13 wheel−. Блокировка действует только на физику; инжект её обходит.
- `SET MOVE_MASK 0x16`: `left:u8 right:u8 down:u8 up:u8`, **без ответа** — те же биты 7, 6, 9, 10, что у
  `0x60`, одной командой. `SET WHEEL_MASK 0x17`: `down:u8 up:u8` → биты 13, 12.
- `GET 0x56 INJECT_SNAPSHOT` (V4.036+): 40 байт; `[0]` инжектированные кнопки (bit0…4), `[1..2]` блокировки u16.
- После команды без ответа следующая проходит через ≥ 1–1.5 мс при неподвижной мыши (2026-10-12), но
  после опроса и с рукой на мыши 2 мс бывает мало (2026-10-30). Транспорт ждёт 3 мс.
- `0x52 INPUT_STREAM`: `GET kind:u8` → `enabled:u8`; `SET kind:u8 enabled:u8` (без ответа). kind 1 = мышь.
- `0x53 INPUT_CHANGE` (незапрошенное): `kind:u8 id:u8 value:u8`, у мыши id = кнопка 0…4, value 0/1;
  `kind FF FF` = переполнение. По UDP приходит с исходным портом, равным порту клиента.
- `0x18 MOVE` по UDP ответа не имеет: потерю не видно, потолок ~280 команд/с. Для эталона не годится.
