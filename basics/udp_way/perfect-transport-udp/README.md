# perfect-transport-udp: замороженный транспорт MAKCU (UDP/Ethernet, batch 0x6C)

> ## ⚠ Обязательная настройка Windows для UDP: брандмауэр
>
> Плата присылает события кнопок `0x53` **с порта, равного порту программы, а не с 8080**. Если сеть с
> платой помечена как **Public** (у нас интерфейс `Ethernet` — Public), брандмауэр Windows **молча
> режет** эти пакеты для любой программы без разрешающего правила. Движение при этом работает, а кнопки
> держатся только на запасном опросе 5 мс (в `statsLine()`: «СОБЫТИЯ НЕ ДОХОДЯТ»).
>
> **Один раз, PowerShell от администратора**, один из вариантов:
>
> ```powershell
> # разрешить входящие UDP только от платы, для любой программы (рекомендуется; у нас сделано 2026-10-12)
> New-NetFirewallRule -DisplayName "MAKCU UDP events" -Direction Inbound -Protocol UDP -RemoteAddress 192.168.50.175 -Action Allow
> ```
>
> или пометить сеть как частную (у нас брандмауэр Private выключен):
>
> ```powershell
> Set-NetConnectionProfile -InterfaceAlias "Ethernet" -NetworkCategory Private
> ```
>
> **Если IP платы сменится** (DHCP), правило с `-RemoteAddress` надо поправить:
> `Set-NetFirewallRule -DisplayName "MAKCU UDP events" -RemoteAddress <новый IP>`.
> Проверка, что правило есть: `Get-NetFirewallRule -DisplayName "MAKCU UDP events"`.

Эталонный рабочий транспорт для сети, вынесенный в одну папку, по образцу
[`../../comport_way/perfect-transport-comport`](../../comport_way/perfect-transport-comport). Он **только
доставляет** целые отчёты `(dx, dy)` в MAKCU по UDP. Темп, нарезка траектории и квантование остаются на
стороне вызывающего кода. Это **единственный путь к ~1000 Гц по Ethernet**: Raw `0x69` по UDP упирается
в ~284 Гц, `0x18` в ~280 команд/с.

**Не править.** Если нужна другая версия, создайте новую папку. Источник: `../makcu_udp_transport.h`
(`RawUdpTransport`, `Format::Batch`) на 2026-10-12. Убраны форматы `0x69`/`0x18`/`0x67`, ведро токенов,
пробы приёма и обёртка HOST.

**Ревизия 2026-10-12 (2): кнопки мыши** (левая, правая, средняя, две боковые): события `0x53` плюс
страховочный опрос `0x55`. Логика движения не менялась. Изменилось окружение цикла: сокет без `connect()`
(события приходят с другого порта платы), поток приёма просыпается по high-resolution таймеру Windows,
а не по `select()`, поэтому опрос идёт по расписанию и без `timeBeginPeriod(1)` у вызывающего.

**Ревизия 2026-10-12 (3): инжект кнопок, блокировки, переподключение.** `press()`/`release()` всех пяти
кнопок (без тайминга: время удержания задаёт вызывающий), блокировки физического ввода (`setLock()`,
14 целей), сверка по снимку платы `0x56` и повтор потерянных команд, автопереподключение с
восстановлением, сброс состояния при `open()` и `close()`. Логика движения не менялась (самопроверка
движения после правки: 2000 из 2000, 99.7–99.8 % интервалов 1 мс).

**Отличие от mover:** если очередь полна (7 записей), `move()` возвращает `false` и дельта остаётся у
вызывающего. В mover в этом случае записи склеиваются. Так сохраняется контракт «один принятый `move()`
= ровно один HID-отчёт». При реальном RTT ~1.9 мс в очереди бывает не больше 3–4 записей, поэтому
это ограничение на практике не срабатывает.

## Использование

```cpp
#include "makcu_udp_batch_transport.h"

makcu::UdpBatchTransport tx;
std::string err;
if (!tx.open("192.168.50.175", 8080, err)) { /* err - причина */ }

// поток тайминга, каждый тик (обычно 1 мс):
pendX += dx; pendY += dy;                      // ваш целый отчёт за тик
if ((pendX || pendY) && tx.move(int16_t(pendX), int16_t(pendY))) pendX = pendY = 0;
// move() == false - дельта остаётся в pend и уйдёт следующим тиком

tx.finish();   // конец движения: дослать очередь, дождаться квитанции, освободить записи (до 300 мс)
tx.close();
```

Кнопки (из любого потока, не блокируют):

```cpp
if (tx.buttonDown(makcu::MouseButton::Side2)) { /* боковая 2 зажата сейчас */ }
uint8_t mask = tx.buttons();                    // bit0 левая .. bit4 side2
uint32_t n = tx.pressCount(makcu::MouseButton::Left);  // нажатий с open(): разность = клики между чтениями
tx.setButtonPollMs(50);                         // страховочный опрос (по умолчанию 50 мс, 0 - выключить)
```

Инжект кнопок и блокировки (из любого потока, не блокируют):

```cpp
tx.press(makcu::MouseButton::Left);             // нажать; удержание - на вашей стороне
tx.release(makcu::MouseButton::Left);           // отпустить
tx.setLock(makcu::LockTarget::Side2, true);     // side2 больше не доходит до игры, но buttons() её видит
tx.setLock(makcu::LockTarget::X, true);         // ось X физической мыши (оба направления)
tx.unlockAll();                                 // снять все блокировки
if (!tx.connected()) { /* связь пропала, транспорт переподключается сам */ }
```

## Контракт

| | |
| --- | --- |
| `open(host, port, err)` | UDP `host:port` (8080), обёртка RAW. `DEVICE 0x02` (маршрут мыши), `FIRMWARE 0x04` ≥ 4097, Raw-метаданные `0x6A(id=0)`, дочистка записей прошлых сессий. `false` + причина: плата не в сети, нет мыши, прошивка без `0x6C` |
| `move(dx, dy)` | **один принятый вызов = ровно одна запись = ровно один HID-отчёт**. Никогда не блокируется на сети. `false` = очередь из 7 записей полна или транспорт неисправен: дельту хранит вызывающий |
| `move(0, 0)` / `service()` | на мышь ничего не уходит. Отправить пакет, если предыдущий уже квитирован (обычно это делает поток приёма) |
| `finish(ms = 300)` | дослать очередь, дождаться квитанции, освободить хвост записей на плате. `true` = всё отдано, плата чистая |
| `stats()` / `statsLine()` | счётчики, можно вызывать из любого потока |
| `buttons()` / `buttonDown(b)` | маска физических кнопок (bit0 левая, 1 правая, 2 средняя, 3 side1, 4 side2). Любой поток, не блокируют. Обновляется событием `0x53` (~1 мс), страховка — опрос `0x55` |
| `pressCount(b)` | нажатий (переходов 0 → 1) с `open()`. Клик не теряется, даже если `buttons()` читают редко. Кнопка, зажатая уже при `open()`, нажатием не считается. Если события режет брандмауэр, клик короче 5 мс может пройти мимо опроса |
| `setButtonPollMs(ms)` | интервал страховочного опроса `0x55`, по умолчанию 50 мс; `0` выключает опрос совсем. Без событий опрос сам идёт не реже 5 мс |
| `press(b)` / `release(b)` / `setButtonState(b, down)` / `releaseAllButtons()` | инжект кнопки (`SET 0x11…0x15`). Уходит следующей командой цикла, **раньше движения** из очереди: ждёт только команду, которая уже в полёте. Замер: от `press()` до события в Windows 1.3–1.55 мс в среднем, max 1.87 мс. Инжект складывается с физикой (ИЛИ): отпускание физической кнопки не отменяет программное нажатие |
| `injectedButtons()` / `injectedButtonsOnBoard()` | запрошенная маска инжектированных кнопок / что на плате по последнему снимку (до 250 мс назад) |
| `setLock(t, on)` / `unlockAll()` / `locked(t)` / `locks()` / `locksOnBoard()` | блокировка физического ввода (`SET LOCK 0x60`): 5 кнопок, оси X/Y и колесо целиком или по направлению. Заблокированное не доходит до ПК от физической мыши; инжект проходит; `buttons()` видит физику и у заблокированной кнопки |
| `connected()` | связь с платой есть. `false` — идёт переподключение, `move()` возвращает `false` |
| `open()` | дополнительно: включает поток событий, приводит плату в чистое состояние — снимает инжектированные кнопки и блокировки, оставшиеся от упавшей программы |
| `close()` | отпускает все инжектированные кнопки, снимает все блокировки (с подтверждением снимком), возвращает поток `INPUT_STREAM mouse` в состояние до `open()` |
| потоки | `move`/`service`/`finish` вызываются **из одного потока**. Внутри свой поток приёма: он же шлёт следующий пакет сразу по квитанции |
| потери | непринятые платой записи (нет места) транспорт возвращает в очередь сам. Нет квитанции 30 мс: опрос `last_accepted_id`, принятое засчитывается, остальное в очередь. Путь не теряется и не дублируется |

Чего транспорт **не** делает: не держит часы и темп, не нарезает траекторию, не копит дробные дельты и не
добавляет шум. Частота HID равна частоте ненулевых принятых `move()` и не выше опроса USB клонированной мыши.

## Как это работает

Каждая UDP-команда идёт на второй чип MAKCU по внутреннему каналу, который везёт одну команду за раз.
Датаграмма, пришедшая во время передачи, **молча выбрасывается** (подтверждено инженерами MAKCU). Поэтому:

- в полёте **один пакет**; следующий уходит из потока приёма сразу по квитанции (closed loop);
- в пакете **до 7 записей**, по одной на тик `move()`. Квитанция сообщает не больше 7 терминальных строк,
  поэтому 16 записей дают ту же скорость: лишние возвращаются с `reason 3` («нет места»);
- поле `X` следующего пакета = старший терминальный id из квитанций (флаг `bit0`): плата освобождает
  записи без отдельных квитанций `0x6A`.

При RTT ~1.9 мс за оборот накапливается ~2 записи, так что пакет в среднем несёт 1.9 записи, а
задержка от `move()` до отправки не больше одного оборота.

## Кнопки мыши

`open()` включает поток событий `INPUT_STREAM mouse` (`0x52 01 01`, без ответа), затем читает стартовую
маску `GET PHYS_BUTTONS 0x55`. Дальше маску держат два источника:

- **события `0x53`**: `55 <nonce> DE AD 03 00 53 01 <id> <0|1>` приходят сразу по нажатию. Внутри стоит
  nonce одной из наших прошлых команд, поэтому транспорт разбирает их по опкоду **до** сопоставления
  ответов по nonce, иначе событие можно принять за квитанцию пакета;
- **страховочный опрос `0x55`** раз в 50 мс в том же замкнутом цикле, что и движение. Он исправляет маску,
  если событие потерялось (UDP не повторяет пакеты). Если события не приходят вообще, а опрос уже дважды
  нашёл изменения, транспорт сам учащает опрос до 5 мс. В `statsLine()` тогда стоит
  «СОБЫТИЯ НЕ ДОХОДЯТ (брандмауэр?)».

`close()` возвращает поток `0x52` в то состояние, в котором он был до `open()`.

**Почему сокет без `connect()`.** Ответы на команды плата шлёт с порта 8080, а события — с порта, номер
которого равен порту клиента (проверено: `from 192.168.50.175:54444` на наш `:54444`). Подключённый сокет
принимает только `плата:8080` и события выбрасывает. Транспорт принимает любые датаграммы с IP платы.

**Брандмауэр Windows.** Если сеть с платой помечена как **Public** и брандмауэр Public включён, события
«с чужого порта» он режет для программы без разрешающего правила. Ответы на команды проходят, поэтому
движение и опрос работают, а события нет. Тогда работает страховочный опрос 5 мс (задержка ≤ ~6 мс, клик
короче 5 мс можно пропустить). Чтобы события доходили, нужно одно из двух (права администратора):

```powershell
# правило только для пакетов от платы, для любой программы
New-NetFirewallRule -DisplayName "MAKCU UDP events" -Direction Inbound -Protocol UDP -RemoteAddress 192.168.50.175 -Action Allow
# или пометить сеть с платой как частную (если брандмауэр Private выключен или там есть правило)
Set-NetConnectionProfile -InterfaceAlias "Ethernet" -NetworkCategory Private
```

Цена для движения: опрос — такая же команда в полёте, как пакет `0x6C`, только ответ быстрее (RTT ~1 мс).
При опросе 5 мс пакеты становятся плотнее (~3 записи вместо ~1.9), а 1000 Гц сохраняются: 2000 из 2000,
99.3–99.9 % интервалов 1 мс.

### Ловушки, на которых ломается интеграция

- **Бинарные `0x11…0x15` (LEFT…SIDE2) физическую кнопку не видят.** Они возвращают только
  инжектированное состояние («софт держит кнопку»), поэтому физическое нажатие там всегда 0. Физику
  дают `0x55 PHYS_BUTTONS`, события `0x53` и текстовые `km.left()…km.side2()` (0 нет / 1 физ. / 2 инж. / 3 обе).
- **Старый поток `0x10 BUTTONS` не нужен.** В режимах 1/2 он вставляет в COM текст `km.<маска>\r\n` между
  бинарными кадрами (его включает SDK mak-suite при connect). Транспорт его не трогает и не разбирает.
- **Каждое включение потока `0x52` начинается с «всё отпущено».** Зажатая кнопка придёт событием только
  со следующим отчётом мыши, поэтому стартовую маску транспорт читает через `0x55` уже после включения.
- **По UDP события `0x53` приходят, но с «чужого» порта.** Плата шлёт их на порт клиента, а исходный порт
  ставит равным порту клиента, не 8080. Сокет с `connect()` такие датаграммы молча выбрасывает (поэтому
  первая проверка показала «0 событий»), а брандмауэр Windows на сети Public режет их для программы без
  разрешающего правила. UDP-транспорт сокет не подключает и страхуется опросом `0x55`.

## Инжект кнопок и блокировки

Команды `SET 0x11…0x15` (кнопки) и `SET 0x60` (блокировки) у платы **без ответа**. Это значит:

- **пауза 2 мс после каждой такой команды.** Замер: следующая команда, пришедшая раньше чем через
  ~1 мс, молча теряется (идёт передача на второй чип); с 1.5 мс проходят 40 из 40;
- **сверка снимком `GET 0x56 INJECT_SNAPSHOT`** (40 байт: `[0]` инжектированные кнопки, `[1..2]` маска
  блокировок, бит = номер цели) сразу после команд и раз в 250 мс. Если на плате не то, что
  отправлено (потерялась датаграмма, плату перезагрузили, вмешалась другая программа), транспорт
  отправляет разницу заново (`stats().repairs`).

Транспорт хранит **запрошенное** состояние (маски кнопок и блокировок), а не очередь команд: несколько
быстрых `press`/`release` подряд схлопываются до итогового состояния. Если нужно гарантированное
нажатие короче оборота цикла, удерживайте кнопку хотя бы несколько миллисекунд.

**Оси в блокировках.** У платы по каждой оси два бита, «+» и «−». Бит оси целиком (`X`, `Y`, `Wheel`)
плата выставляет сама, когда заблокированы оба направления. Замер: «+X, затем −X» → `{X,+X,−X}`;
«X, затем снять +X» → `{−X}`. Поэтому `setLock(X, on)` ставит или снимает оба направления, а
`setLock(XPos, false)` при заблокированной оси оставляет только −X.

## Переподключение

Опросы и снимки работают как пульс: если от платы нет ни одной датаграммы 750 мс, связь считается
потерянной. Тогда:

- `connected()` и `healthy()` дают `false`, `move()` возвращает `false`. Записи движения, не дошедшие до
  платы, сбрасываются (`stats().droppedRecords`): к моменту восстановления они устарели. Пример и тест
  в это время тоже сбрасывают накопленную дельту, чтобы не было рывка;
- сторожевой поток раз в 250 мс пробует рукопожатие заново. После успеха он продолжает id записей,
  включает поток событий, перечитывает кнопки и по снимку дошлёт запрошенные блокировки и кнопки
  (после перезагрузки платы они пропадают);
- замер: кабель хаба выдернут на несколько секунд → обрыв замечен, через 14.3 с (линк сетевой карты +
  DHCP платы) связь восстановлена сама, блокировка на месте, движение продолжилось.

**Ограничение.** Если в момент `close()` связи нет или программа упала, не дойдя до `close()`, зажатые
программой кнопки и блокировки **остаются на плате**: прошивка не отпускает их сама. Их снимет
следующий `open()` этого транспорта (он приводит плату в чистое состояние) или перезагрузка платы.
Ставьте обработчик Ctrl+C и закрытия консоли, который вызывает `close()`.

## Требования

- Прошивка с batch `0x6C`: **V4.097** и новее. С 2026-10-11 V4.097 — официальная прошивка MAKCU;
  V4.095 и старее `0x6C` не умеют, на них `open()` вернёт ошибку.
- Сеть MAKCU: USB-Ethernet в USB3-порту платы. Проверено на хабе **UGREEN 60554** (Genesys Logic
  `05E3:0610` + гигабитный NIC **ASIX AX88179 `0B95:1790`**), мышь в том же хабе, PC → свитч → RJ45 хаба.
  Внешнее питание хаба по USB-C на результат не влияет.
- Мышь в host-порту MAKCU опрашивается на 1000 Гц: плата копирует её интервал опроса.
- Сам транспорт «Повышенную точность указателя» не трогает. Для точного пути в Windows её выключает
  вызывающий.

## Протокол на проводе (для справки)

Датаграмма: `0x55 | nonce u64 | DE AD | LEN u16 | CMD u8 | PAYLOAD`. Ответ несёт тот же nonce, payload
с байта 14. Одна команда на датаграмму.

- `0x6C BATCH` (V4.097+): `01 | flags | N | 00 | X u32 | N × [id u32 | x i16 | y i16 | dt u16]`, длина
  ровно `8 + 10N`. `flags bit0`: освободить терминальные записи с `id ≤ X`. `X` не больше старшего
  терминального id, уже сообщённого квитанцией, иначе `255 / reason 1` без последствий.
- Квитанция: `[0]=1 [1]=0 все / 1 частично / 255 отклонено [2]=N [3]=принято [4]=первый отказ
  [5]=причина [6]=освобождено [7]=свободно [8]=K строк (≤ 7) [9]=more [10]=в очереди [11]=0
  [12..15]=last_id`, затем `K × (id u32 | state u8 | reason u8)` по возрастанию id. Записи принимаются
  подряд с первой; `state 2` = отдано в USB-endpoint, `3` = отказ.
- `0x6A RAW_ACK`: `id = 0` → метаданные `schema, last_accepted_id, free_records, capacity (16)`;
  `(id, consume = 1)` → освободить терминальную запись (дочистка хвоста в `open()`/`finish()`).
- ID строго растут в пределах загрузки платы. Ёмкость платы 16 записей.
- `0x55 PHYS_BUTTONS` (V4.036+): пустой запрос → `mask:u8` физических кнопок. Ответ ~1 мс.
- `SET 0x11…0x15` (LEFT…SIDE2): `state:u8` (1 нажать, 0 отпустить), **без ответа**. `GET` тех же опкодов
  отдаёт только инжектированное состояние, не физику.
- `SET LOCK 0x60`: `target:u8 state:u8`, **без ответа**; `GET LOCK 0x60 target:u8` → `state:u8`. Цели:
  0 left, 1 right, 2 middle, 3 side1, 4 side2, 5 X, 6 +X, 7 −X, 8 Y, 9 +Y, 10 −Y, 11 wheel, 12 wheel+,
  13 wheel−. Блокировка действует только на физику; инжект её обходит.
- `GET 0x56 INJECT_SNAPSHOT` (V4.036+): 40 байт; `[0]` инжектированные кнопки (bit0…4), `[1..2]` блокировки u16.
- После команды без ответа следующая проходит через ≥ 1–1.5 мс (замер 2026-10-12).
- `0x52 INPUT_STREAM`: `GET kind:u8` → `enabled:u8`; `SET kind:u8 enabled:u8` (без ответа). kind 1 = мышь.
- `0x53 INPUT_CHANGE` (незапрошенное): `kind:u8 id:u8 value:u8`, у мыши id = кнопка 0…4, value 0/1;
  `kind FF FF` = переполнение. По UDP приходит с исходным портом, равным порту клиента.
- `0x18 MOVE` по UDP ответа не имеет: потерю не видно, потолок ~280 команд/с. Для эталона не годится.
