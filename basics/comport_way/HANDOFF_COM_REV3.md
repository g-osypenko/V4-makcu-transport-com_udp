# Передача: перенести ревизию 3 в COM-эталон (2026-10-12)

Задача следующего чата: довести `perfect-transport-comport/makcu_raw_transport.h` (COM, Raw `0x69/0x6A`)
до уровня UDP-эталона ревизии 3. Образец — `basics/udp_way/perfect-transport-udp/` (код, README,
`controls_test.cpp`). Общий обзор проекта — корневой `CONTEXT_AND_SETUP.md` (читать первым).

## Что уже есть

- **UDP-эталон, ревизия 3** (`makcu_udp_batch_transport.h`): движение 1 кГц (`0x6C`), чтение кнопок
  (события `0x53` + страховочный опрос `0x55`), **инжект кнопок** `press/release` (`SET 0x11…0x15`),
  **блокировки** `setLock/unlockAll` (`SET 0x60`, 14 целей), сверка по снимку `GET 0x56`,
  **автопереподключение**, сброс состояния в `open()`/`close()`. Проверено на железе: клики 25/25,
  ~1.5 мс до Windows; блокировки (транспорт видит, Windows нет); переподключение после выдернутого кабеля.
- **COM-эталон, ревизия 2**: движение 1 кГц (`0x69/0x6A`) + чтение кнопок (события `0x53` по COM,
  `0x55` при открытии и после переполнения). Инжекта, блокировок, переподключения **нет**.
- Тестовая программа UDP `controls_test.exe`: `--clicks`, `--draw S`, `--watch S`, `--locks S`,
  `--reconnect S`, `--soak M`; своё окно с `ClipCursor`, рисует след и точки, статус вверху, Esc — выход.

## Решения владельца (не переспрашивать)

- Клики **как можно быстрее**, без упорядочивания с движением. Без тайминга и «хуманизации»: время
  удержания задаёт вызывающий.
- **Колесо не нужно** вообще (на 4097 читать физическое колесо и нельзя).
- **Автопереподключение + при `close()` отпустить все кнопки и снять все блокировки.**
- Долгий прогон — 30 минут.
- Делать по образцу UDP: тот же API (`press/release/setButtonState/releaseAllButtons`, `injectedButtons*`,
  `setLock/unlockAll/locked/locks/locksOnBoard`, `connected()`), общий блок `LockTarget` с защитой
  `MAKCU_LOCK_TARGET_DEFINED` (оба заголовка должны собираться в одной программе).

## Что перенести и чем COM отличается от UDP (проверить замерами, не переносить вслепую)

1. **Инжект и блокировки.** `SET 0x11…0x15 state`, `SET 0x60 target state` — без ответа. По UDP после
   такой команды нужна пауза ≥ 1–1.5 мс (иначе следующая теряется). **По COM этого ограничения, скорее
   всего, нет** (COM держит > 2000 кадров/с, кольцо из 32 записей WriteFile) — замерить: SET + сразу
   GET, без паузы. Кадры COM уходят из потока `move()` через кольцо `sendFrame()` → `press()` из любого
   потока нельзя слать напрямую: хранить «запрошенное» в атомиках, отправлять из `move()/service()`
   (как сделан `resyncButtonsIfNeeded()`), либо добавить свою блокировку на кольцо.
2. **Сверка снимком `GET 0x56`** (40 байт: `[0]` инжект-кнопки, `[1..2]` блокировки u16) — ответ
   разбирать в `parseRaw()` (опкод `0x56`, длина 40). Нормальная форма блокировок как в UDP: по оси два
   бита (+/−), бит оси целиком только вычисляется (`normalizeLocks`, `applyLock`).
3. **Переподключение по COM** = другая природа обрыва: выдернут USB2 / перезагрузка платы → `WriteFile`
   / `ReadFile` с ошибкой, COM-порт исчезает. Нужно: заметить (ошибка ввода-вывода или тишина при
   пульсе), закрыть хэндл, ждать появления порта (`findMakcuPorts()`), переоткрыть (проба скорости
   4М/1М/115200), заново `prepareRaw()`, поток событий, восстановить блокировки/кнопки по снимку.
   Сейчас COM-транспорт при ошибке ставит `failed_` навсегда.
4. **`open()`/`close()`**: снять остатки упавшей программы при открытии; при закрытии отпустить и
   разблокировать (с подтверждением снимком), вернуть поток `0x52`.
5. Тест: сделать COM-вариант `controls_test` (или режим `--com` в общем) с теми же режимами.

## Факты, ловушки

- COM: CH343 `1A86:55D3`, у нас **COM5, 4 000 000 бод**; порт эксклюзивный. USB2 сейчас может быть
  отключён — попросить владельца подключить перед тестами. `MAKCU Virtual COM Port (COM8)` — это канал
  Toolkit, не наш.
- `GET 0x11…0x15` отдают **только инжект**, не физику. Физика — `0x55`/`0x53`.
- Блокировка: игра не видит, транспорт видит (события описывают физику до блокировки).
- Инжектированные кнопки и блокировки прошивка сама **не снимает**.
- Прошивка **V4.097 официальная** с 2026-10-11. Тест-сборки V4.098 (USB3-сторона сама перезапускается
  после зависания) и V4.099 (+ придерживание инжекта у беспроводных ресиверов после 9–18 с простоя).
  В 30-минутном UDP-прогоне на 3-й минуте USB3 платы «замолчал» (мышь и сеть умерли, помогло только
  переподключение) — симптом из описания 4098. Транспорт тут ни при чём; при повторе — просить 4098/4099.
- Тесты двигают курсор и кликают — только в своём окне с `ClipCursor`; владелец во время прогона не
  трогает мышь; давать ему Esc для выхода. Реверс прошивки не делаем.
- Сборка: MinGW g++ 15.3 (`C:\mingw64\bin`), эталоны C++17, `-Wall -Wextra` без предупреждений.

## Как начать

1. Прочитать `CONTEXT_AND_SETUP.md`, этот файл, `perfect-transport-udp/README.md` (разделы «Инжект кнопок
   и блокировки», «Переподключение») и код `perfect-transport-comport/makcu_raw_transport.h`.
2. Попросить подключить USB2 (COM5), проверить `perfect-transport-comport/example_line.exe --check`.
3. Пробами замерить: нужна ли пауза после `SET` по COM; формат ответа `0x56` по COM.
4. Реализовать ревизию 3 COM, затем тесты (`--clicks`, `--locks`, переподключение — выдернуть USB2,
   долгий прогон), обновить README и `CONTEXT_AND_SETUP.md`, закоммитить.
