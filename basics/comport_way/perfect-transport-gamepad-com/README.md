# perfect-transport-gamepad-com: транспорт и рендерер геймпада MAKCU по COM

Состояние на **2026-11-20**. Транспорт - ревизия 4 (живучесть, §4.3а; на плате ещё не запускалась), рендерер - ревизия 4. Плата MAKCU, прошивка **4133** (персональная
сборка разработчиков, до неё официальная 4126; замеры ниже помечены прошивкой). Геймпад для всех замеров один: **GameSir
в режиме XInput** (`kinds 0x82`), сначала по кабелю, с 2026-11-16 по радио через свой приёмник в порту геймпада платы.

Подробная история, все прогоны и журналы: `HANDOFF_GAMEPAD_COM.md` в корне репозитория (разделы указаны как §N).
Этот файл - контракт и итоговые цифры. Если что-то здесь расходится с HANDOFF, верен HANDOFF (он новее), и надо исправить здесь.

## 0. Главное за 30 секунд

- **Плата сейчас роняет геймпад под нагрузкой по COM.** Отказ USB3 платы: геймпад пропадает из Windows и с платы.
  На 4126 - навсегда до переподключения платы, на 4133 - сам возвращается за 1.4-2 с. Темп, при котором видели отказ:
  2000 чтений `0x54`/с (4126: 5 из 5 за 4-108 с; 4133: 1 раз за 3 прогона по 300 с), 500 чтений + ~325 команд/с
  (4133: на 987-й с из 1200), 1000 команд + 100 чтений/с (4126: на 10-й с; 4133: на 130-й с). **MAKCU 2026-11-17:
  причина найдена, исправление в тестировании, новую сборку пришлют.** До неё безопасного темпа нет (§7).
- **2026-11-20 (4133): безопасного темпа по COM нет** - даже 500 чтений + 250 команд/с то проходят 300 с, то дают отказ
  на 37-й с и бурю; отказ зависит от состояния платы больше, чем от темпа (HANDOFF §9м). Поэтому ревизия 4 транспорта
  делает упор на живучесть (§4.3а), а умолчания - самая мягкая рабочая нагрузка: **команды раз в 4 мс (250/с) при любом
  режиме, опрос `0x54` раз в 4 мс (250/с; решение владельца: стик - абсолютная величина, 250/с хватает)**, оба не чаще
  интервала геймпада. До ревизии 4: команды 2 мс при Auto / 1 мс при Off.
- **Лучшая текстура - сглаживание платы Off + команды раз в 1 мс + `presetOff()`: сумма W1 3.49** до живой руки
  (гладкая кривая 15.70). Но 1000 команд/с - как раз тот темп, который режет отчёты геймпада и роняет USB3. Пока
  исправления нет, рабочий режим - Auto, 500 команд/с, W1 ~7-8.
- COM-порт читается **только без ожидания**: тайм-ауты чтения с драйвером WCH CH343 давали синий экран (§9).

## 2. Использование

```cpp
#include "makcu_gamepad_raw_transport.h"
#include "makcu_gamepad_renderer.h"

makcu::GamepadRawTransport tx;
std::string err;
// tx.setSmoothing(0);              // по желанию: Off кодом на время работы, close() вернёт прежнее (§4.6)
if (!tx.open("", err)) { /* err: порт не найден или плата не ответила */ }
// геймпада может ещё не быть: tx.controllerKind() == 0, транспорт ждёт его сам

makcu::PadTextureRenderer r;
r.setProfile(makcu::PadTextureRenderer::presetForTransport(tx.controllerKind(), tx.boardSmoothingOff(),
                                                           tx.commandPeriodUs(), tx.padCadenceUs()));
const makcu::PadPhysical p0 = tx.physical();
r.beginEvent(seed, p0.rx, p0.ry);
for (;;) {                       // один шаг рендерера = одна команда плате
    int16_t ox, oy;
    r.step(targetX, targetY, ox, oy);   // цель в координатах платы, +Y ВНИЗ
    tx.setRightStick(ox, oy);
    tx.waitCommand();            // дождаться, пока команда ушла
}
tx.releaseRightStick(100);       // ОБЯЗАТЕЛЬНО: иначе стик останется зажатым
tx.close();
```

Порт эксклюзивный: MAKCU Toolkit и SDK mak-suite должны быть закрыты. Toolkit, открытый одновременно, получит отказ.

## 3. Ось, нули и единицы (ловушки)

- **Ось Y на плате направлена ВНИЗ**: -32768 = стик вверх до упора. В Windows XInput наоборот, пересчёт точный:
  `sThumbRY = -ry - 1` (замер: ry -12000 -> Windows +11999). `padToXInputY()` / `padFromXInputY()`. Ось X совпадает.
- **`(0, 0)` в `SET 0x40` - это не центр, а «отпустить стик»** (zero-state handoff). Центр под управлением программы -
  `(0, -1)`, в Windows это ровно `(0, 0)`. `setRightStick(0, 0)` транспорт сам шлёт как `(0, -1)`.
- Покой физического стика GameSir - ровно `0, -1` (на 4122 однажды было `-912, 265`).
- Триггеры 0..1023, в Windows значение / 4 (1023 -> 255, 512 -> 128, 4 -> 1).
- `cadence`, `dt`, `usb_timestamp` в `0x54` - в единицах 125 мкс (8 = 1 мс). `km.device()` - интервалы в микрокадрах (`C:8uf`).

## 4. Контракт транспорта (`GamepadRawTransport`)

Все методы можно звать из любого потока. На порту блокируются только `open()`, `close()`, `releaseRightStick(waitMs > 0)`,
`clearAllOverrides()`, `setSmoothing(..., waitMs)` - ждут подтверждения не дольше заданного.

### 4.1 Открытие, закрытие, переподключение

- `open(port, err)`: пустая строка - первый найденный MAKCU (`1A86:55D3`). Подбирает скорость (4 000 000, 1 000 000, 115 200),
  читает прошивку, тип геймпада, настройки, снимает оставшийся перехват (`SET 0x40` нулями + сверка `GET 0x40`).
  `true`, если плата отвечает; геймпада может не быть.
- `close()`: отпускает стик и кнопки с подтверждением, возвращает сглаживание платы, если его менял `setSmoothing()`.
- Связь: ошибка ввода-вывода или молчание платы 750 мс - порт закрывается и ищется заново раз в 250 мс; после
  восстановления перехват снят, вызывающий просто продолжает слать `setRightStick()`. Переподключение платы
  выдёргиванием USB2 **не проверено**.
- Геймпад пропал (`0x02` = 0): транспорт спрашивает `DEVICE` раз в 0.5 с; когда геймпад появился - заново читает
  настройки и применяет желаемое сглаживание. **Живьём на 4133-отказе (геймпад пропадает на 1.4-2 с) этот путь ещё не
  проверен** - `pad_soak` на отказе выходит.

### 4.2 Правый стик

- `setRightStick(rx, ry)` / `aim()`: не блокируется, значение ложится в слот, рабочий поток шлёт самое свежее раз в
  `commandPeriodUs()` (latest-wins, без суммирования). Пока перехват активен, команда повторяется каждый период, даже если
  цель не менялась.
- `releaseRightStick(waitMs)`: нули; при `waitMs > 0` ждёт, пока `GET 0x40` вернёт нули. `clearAllOverrides()` - стик и кнопки.
- `waitCommand(timeoutMs)`: дождаться отправки очередной команды - так рендерер шагает ровно раз на команду. Значение,
  заданное сразу после `waitCommand()`, уходит следующей командой (это +1 период отставания).
- `injecting()`, `commandCount()`.

### 4.3 Период команд и опроса (ревизия 3)

| Что | По умолчанию | Задать |
| --- | --- | --- |
| `commandPeriodUs()` | **4000 мкс при любом режиме (ревизия 4**; до неё 2000 при Auto / Fixed, 1000 при Off); **не короче `padCadenceUs()`** | `setCommandPeriodUs(us)`, не меньше 1000; `us <= 0` - снова по умолчанию; тоже не короче `cadence` |
| `physicalPollUs()` | **max(4000, `cadence`)** (ревизия 4; в ревизии 3 max(2000, ...)), не больше 32 000 | `setPhysicalPollUs(us)` 500..10 000 берётся как есть (для проб); `us <= 0` - снова авто |

Почему так:
- Клон геймпада на плате объявляет Windows тот же интервал опроса, что и настоящий геймпад (`cadence` из `0x54`,
  в документации «configured report cadence»). Чаще интервала плата отчёт не отдаст, лишние команды только грузят COM.
  Геймпад 125 / 250 / 500 Гц -> команда раз в 8 / 4 / 2 мс. **На настоящем медленном геймпаде не проверено**: у нас
  только GameSir с `cadence` 1 мс.
- Опрос `0x54` до ревизии 3 шёл каждые 500 мкс (2000/с) - это темп, на котором плата роняет USB3 (§7).
- `padCadenceUs()` - объявленный интервал, `padReportRate()` - измеренная частота (прирост `sequence` за 0.5 с; 0 без
  геймпада). Если геймпад шлёт заметно реже объявленного (GameSir с открытым GameSir Connect: ~225 отчётов/с при `cadence`
  1 мс), свободные слоты клона заполняет инжект: 225 + 500 команд/с дали в Windows ~722 пакета/с (§9к HANDOFF). Тогда
  вызывающий может поставить `setCommandPeriodUs(1e6 / padReportRate())`.
- **Пока идут команды, плата получает от геймпада меньше отчётов**: при командах раз в 2 мс ~500/с вместо 1000 (видно
  в `padReportRate()`), раз в 1 мс - ~495/с на 4126 и ~660/с на 4133, раз в 4 мс - тоже ~500/с (4133, 2026-11-20).
  Это свойство платы, не транспорта. **Поэтому опрос чаще 500/с под инжектом новых значений не даёт.**

### 4.3а Живучесть (ревизия 4, 2026-11-20; собрано, на плате ещё не запускалось)

На 4133 геймпад пропадает с платы при любом темпе и сам встаёт за ~2 с; после первого отказа бывает буря. До ревизии 4
транспорт всё это время бил плату на полном темпе (опрос, `SET 0x40`, починки сверки) - вероятный катализатор бури.

| Состояние | Как распознаётся | Что делает транспорт | API |
| --- | --- | --- | --- |
| Геймпада нет (отказ платы, вынут, уснул) | `DEVICE` -> `kinds 0` или 3 ответа `FF` на `0x54` подряд | `SET 0x40` не шлются, сверки нет, опрос `0x54` раз в 50 мс; после нового `sequence` ещё 250 мс тишины, затем инжект продолжается сам (при Off - с плавным входом). `setRightStick()` звать как обычно | `padAbsent()`, `commandsSuspended()` |
| Буря | 3 отказа за 60 с | опрос `0x54` не чаще 100/с до 60 с после последнего отказа | `stormActive()` |
| Геймпад завис (GameSir, 2026-11-20) | снимки `0x54` идут, `sequence` стоит > 300 мс (`timing INVALID`) | инжект продолжается (плата отдаёт его Windows), рука не доходит; лечит только перезапуск самого геймпада - сказать пользователю | `padStalled()` |

В `Stats` и `statsLine()`: `padDrops`, `padStalls`, `storms`, `lastPadDownMs` и текущие флаги. При открытии без геймпада
команды ждут его появления (это не отказ). Не проверено: геймпады, которые шлют отчёты только при изменениях (для них
`padStalled()` сработает ложно); помогает ли пауза против бури (нужен прогон).

### 4.4 Плавный вход и выход (`setBlendMs(enterMs, exitMs)`)

На плату уходит `физика + (цель - физика) * smoothstep(w)`, `w` 0 -> 1 за `enterMs` после первого `setRightStick()` и
1 -> 0 за `exitMs` после `releaseRightStick()`; нули уходят, когда `w` дошёл до 0. Физика - свежий снимок `0x54` (с
ревизии 3 не старше ~2 мс). По умолчанию (отрицательные значения): **при Off 16 и 24 мс, при Auto / Fixed 0** (плата
сглаживает сама). Замер (V4.122, ступенька 12 821 единица): наибольший шаг между пакетами Windows 1187-1196 на входе и
794-800 на выходе против скачка 12 821 без перехода и ~4000 при ходе самой платы в Auto. Числа 16 / 24 мс на «похожесть на
руку» не проверялись. Переход при движущейся руке не мерили.

### 4.5 Кнопки и триггеры

- `setButton(id, down)`, `setTrigger(id, 0..1023)`, `tap(id, holdMs = 60, triggerValue = 1023)` (отпускает рабочий
  поток), `releaseButtons()`, `buttonInjected(id)`, `triggerInjected(id)`.
- Правило платы: бит 1 - кнопка нажата программой, 0 - проходит физическая; триггер 1..1023 - значение программы, 0 -
  физический. **Программа может нажать, но не может отжать кнопку, которую держит рука** (нужна маска `0x51`, её нет).
- Пока стик не перехвачен, изменение уходит на ближайшем такте (до 0.5 мс) и повторяется раз в 100 мс (сторож молчания
  платы 1 с); пока перехвачен - едет в команде стика.
- Контролы: 0-3 A/B/X/Y (SOUTH/EAST/WEST/NORTH), 4-7 крестовина, 8-9 бамперы, 10-11 триггеры, 16-17 нажатия стиков,
  18 SELECT, 19 START, 20 MODE, 21-22 GRIP, 23-54 EXTRA. **Задние кнопки GameSir дублируют A и B внутри геймпада, плата
  их отдельно не видит.** Перед тестами кнопок закрыть Steam (раскладка рабочего стола превращает нажатия в клики и Enter).

| Замер (Off, V4.122 / 4126, кабель) | Результат |
| --- | --- |
| `tap()` RT / LT / A / B / RB / R3 / крестовина, 30 нажатий | 30 из 30, в Windows через 2.3-5.4 мс, длительность ±1 мс от заданной |
| удержание 3.2 с RT, A, RT + A | держатся всё время, отпускание через 3.5-5.3 мс |
| круг стиком + `tap(RT, 80 мс)` каждые 250 мс | 6 из 6, средняя длительность 80.2 мс |

### 4.6 Сглаживание платы кодом

- `setSmoothing(0 | 1 | 2, waitMs)` (Off / Fixed / Auto), `setSmoothingBuffer(ms)` (1..64, звать до `setSmoothing()`),
  `keepSmoothingOnClose(bool)`, `boardSmoothingOff()`, `settings()`.
- Документированная запись `0x3E` / `0x1D` (`mak-suite/protocol/DEVICE_SETTINGS.md`): INFO, READ, BEGIN, WRITE x5 (все
  400 байт), APPLY; при ошибке DISCARD. Меняется только u32 по смещению 4 (интерполяция) и, если задан, по смещению 8
  (буфер). **SAVE не шлётся - в NOR ничего не пишется**, перезагрузка платы возвращает сохранённое.
- `close()` возвращает значение, бывшее до первой удачной записи. **Если программа упала, на плате остаётся заданное**
  до перезагрузки платы или Toolkit, и следующий `open()` примет его за исходное.
- Проверено (V4.122): Auto -> Off -> Auto кодом, `close()` вернул прежнее, 4 записи без сбоев.

### 4.7 Чтение физического геймпада

`physical()` -> `PadPhysical`: кнопки (55 контролов), LT/RT, оба стика, `sequence`, `usbTimestamp`, `dtUframes`,
`cadenceUframes`, `ageUs`, `live` (снимок моложе 50 мс), `samples`. `buttonDown(id)`, `pressCount(id)` (фронты по
снимкам). Отказ `FF` на `0x54` прежний снимок не затирает. Опрос - раз в `physicalPollUs()`, поэтому между опросами
отчёты пропускаются (счётчик `skipped`).

### 4.7а Поток физики вместо опроса (`setPhysicalSource`, 2026-11-17, НА ПЛАТЕ НЕ ПРОВЕРЕНО)

- `setPhysicalSource(PhysicalSource::Stream, periodMs = 1)` - можно до `open()` и после; `PhysicalSource::Poll` - вернуться.
  `physicalSource()`, `streamActive()`; в `Stats` - `streamWanted`, `streamActive`, `streamUnsupported`, `streamEvents`,
  `streamUnavailable`, `streamWrites`, `streamFailures`; `statsLine()` дописывает «поток 0x73/0x74: ...».
- Включение (синхронно, в `open()`, при появлении геймпада, по просьбе, при повторе): `0x73` и `0x74` с пустым телом
  (ответ `mode u8 + period u16 LE`); если не `2, periodMs` - `SET [2, period]` и снова запрос со сверкой. **Ответ `FF` - команды
  нет в этой прошивке: `streamUnsupported`, транспорт остаётся на опросе и больше 0x73 / 0x74 не трогает.**
- События `0x75` (kind 1 - оси id 10-15: LT, RT, LX, LY, RX, RY; kind 2 - кнопки, value 0/1; id 255 - снимок недоступен)
  обновляют `physical()` и счётчики нажатий сразу. `GET 0x54` в потоке - раз в 250 мс (sequence, cadence, частота, live);
  снимок «живой» 625 мс (стоящий стик событий не шлёт).
- Раз в 1 с транспорт спрашивает состояние потоков; выключились (по документации - после переподключения; возможно, после
  перезапуска USB3) - включает снова. `close()` выключает (mode 0). В режиме `Poll` транспорт `0x73` / `0x74` не шлёт вообще.
- Минусы: в событиях нет `sequence` и времени отчёта; во время синхронных обменов (настройки, включение потока) события
  пропускаются, оси и кнопки догоняет ближайший снимок `0x54` (до 250 мс); пропажа геймпада замечается за ~0.6 с, а не 50 мс.
- Источник формата: makcu.com, раздел API (`km.controller_axes` / `km.controller_buttons`, «since V4.105 (test build)»).
  Есть ли команды в официальных сборках, документация не говорит. MAKCU 2026-11-17: «должно быть легче опроса», данных нет.
- Проверка (после новой прошивки): `example_pad.exe --check --stream` - строка `[+] --stream 1 мс: поток ... включён` или
  `НЕ ПОДДЕРЖИВАЕТСЯ`; затем `example_pad.exe --buttons 20 --stream` (жать кнопки, двигать стики) - нажатия печатаются,
  «событий» в строке статистики тысячи.

### 4.8 Статистика

`stats()` / `statsLine()`: связь, тип геймпада, **интервал и частота отчётов, оба периода**, запросы `0x54`, новые
отчёты, отказы `FF`, без ответа, пропущено; команды стика (интервал средний / наибольший), отпускания, команды кнопок,
отказы `0x40`, сверки, починки; опоздание такта; обрывы связи, восстановления. `info()` - строка о подключении.

### 4.9 Чего транспорт не делает

Не смешивает инжект с рукой (это вызывающий или плата), не трогает левый стик, не отжимает кнопки руки, не пишет в NOR,
не включает потоки событий без просьбы (`setPhysicalSource`, §4.7а), не знает об «уступке руке через 2 с» (§6.3).

### 4.10 Устройство

Один рабочий поток, синхронный порт, такт 500 мкс (таймер высокого разрешения + короткое активное ожидание). В начале
такта читается всё пришедшее (без ожидания), в конце уходят запросы: `GET 0x54` раз в `physicalPollUs()`, `SET 0x40` раз
в `commandPeriodUs()`, `GET 0x40` раз в 250 мс (и через 5 мс после отпускания или починки). Ответы разбираются на
следующем такте. Сверка: `GET 0x40` сравнивается с отправленным (все 20 байт), расхождение - команда повторяется.

## 5. Рендерер (`PadTextureRenderer`)

Цель - чтобы поток значений стика, который видит игра, был неотличим от живой руки на этом геймпаде. Мера - сумма W1 по
`PadTexture19` (19 описателей: доля полок, длины пробегов, автокорреляции приращений, полосы 8-14 / 18-28 / 120-500 Гц ...).

- Жизненный цикл: профиль (`presetForTransport()`, `presetOff()`, `presetFor()`, `loadProfile()` или 256 живых снимков через
  `observePhysical()` -> `prepareProfile()`), затем на каждое ведение `beginEvent(seed, rx0, ry0)` и `step(tx, ty, ox, oy)`
  раз на команду. Целые Q16 / Q14, шум SplitMix64 - одинаково на любой машине; без кучи в горячем пути.
- **`presetForTransport(kind, boardOff, commandPeriodUs, padCadenceUs)` (ревизия 4) - пользоваться им.** Выбирает
  `presetOff()` / `presetFor()` по режиму, ставит такт = период команд, частоту геймпада = 1e6 / `cadence`, подгоняет
  модель АЦП: выборка раз в round(2 мс / период) тактов; при такте от 2 мс - каждый такт свежая выборка, без середины.
  На 1 мс / 1000 Гц / Off выход побитно равен `presetOff()` (проверка без железа, 20 000 шагов). Просто менять `tick_hz`
  нельзя: при такте 8 мс модель `presetOff()` брала бы выборку раз в 16 мс.
- **`presetOff()` - модель АЦП GameSir** (замер записи живой руки по кабелю, 1000 отчётов/с): разряд ~101 единица в «сырых»
  координатах, радиальная кривая отклика `s = r - 0.5 * 8600 * (1 - exp(-r / 8600))`, обрезка по кругу 33 750, выборка
  раз в 2 мс, промежуточный отчёт - середина, пачки «без середины» (0.005, длина 6), гистерезис 0.75 разряда, тремор и
  резонанс малые, межосевая связь 0, без опережения.
- `presetFor()` - под Auto: такт 2 мс, опережение `kappa 1` (обращает `y = 0.5u + 0.5y_пред` интерполятора), шесть
  каскадов (тремор AR(2) ~10 Гц, резонанс ~22 Гц, межосевая связь, люфт, сетка с гистерезисом, выборка-хранение).
- Пресеты Sony8bit / Xbox10bit / Hall12bit - по документации, на живых геймпадах **не проверены**.

| Замер на плате (V4.122, Off, 7 с, 7000 команд раз в 1 мс, `pad_bench_20261115_off2.log`) | Отставание | Ошибка слежения ср. / p99 | Сумма W1 |
| --- | --- | --- | --- |
| гладкая кривая | 5.50 мс | 5.4 / 147 | 15.70 |
| **рендерер `presetOff()`** | **7.50 мс** | **79.9 / 226** | **3.49** |
| повтор записи руки как есть | 5.50 мс | - | 1.23 |
| (при Auto, команды раз в 2 мс) повтор записи руки | - | - | 6.9-8.2 - потолок задаёт плата |

- Симулятор `../pad_probes/pad_render_sim.exe` сходится с платой (3.25 против 3.49): при Off плата прозрачна, рендерер
  подбирается без железа (`sweep_render.ps1`).
- Рендерер добавляет **2 мс отставания** (выборка раз в 2 мс + середина). Упреждение цели на 2 мс владелец делает в
  вызывающем коде, не здесь.
- 500 команд/с при Off (симулятор): сумма W1 7.3-9.9 - как Auto. Fixed с буфером 1 мс на 500 командах/с: 4.39, но прогон
  незачётный (геймпад уже молчал).
- `step()`: 70-91 нс (без железа), 376 нс в среднем внутри живого круга (`example_pad`, 2026-11-17).

## 6. Что плата делает с инжектом (замеры)

### 6.1 Сглаживание Auto против Off (V4.122, кабель)

| Что | Auto (буфер 8 мс) | **Off** |
| --- | --- | --- |
| ступенька от покоя | S-образный ход, 100 % через 11-12.6 мс | один скачок через 3.4-4.6 мс |
| отпускание нулями | плавно, покой через 11.6-14.7 мс | скачок в физику через 4.5-5.7 мс |
| команды раз в 1 мс | плата берёт цель раз в 3 мс, 2/3 теряются | берёт каждую |
| команды раз в 2 мс | `y = 0.5u + 0.5y_пред`, задержка 3 команды, отставание 6-7 мс | лесенка по 2 мс |
| движущаяся цель | отставание 6-7 мс, сглаживание | чистая задержка 4.0-5.0 мс, значения без изменений |
| редкие команды (4, 8, 50 мс) | интерполяция между командами | лесенка |

Fixed (4126): середины не ставит, шаг команды делится на малую и большую части (буфер 1 мс: 70 + 130 из 200; 2 мс:
22 + 178; 8 мс: 12 + 187). Переключает режим владелец в Toolkit (Controller -> Smoothing) или код (`setSmoothing`).

### 6.2 Сторож молчания 1 с

Одна команда и тишина: цель держится **1004.6 мс**, затем выход мгновенно прыгает в физику, а `GET 0x40` продолжает
возвращать прежнюю цель (сверка этого не видит). В документации сторожа нет. Поэтому транспорт повторяет команду каждый
период и кнопки раз в 100 мс. Проверено при Auto; при Off не проверено.

### 6.3 Уступка движущейся руке через 2 с

Если цель **не меняется** 2 с с начала инжекта, а рука двигает стик, выход уходит за рукой (2003.7-2059.9 мс), отставание
7.5 мс. Пока цель меняется - рука не влияет вовсе. Стик, неподвижно прижатый рукой, не перехватывает. Пороги «цель не
меняется» (между ±1 и ~38 ед/мс) и «рука движется» (между ~5 и ~25 ед/мс), возврат управления команде - не измерены.
Проверено при Auto; при Off не проверено. Транспорт об этом не сообщает.

### 6.4 Прочее

- Задержка физики через плату без инжекта: 0.25-0.75 мс, значения 1:1.
- Документированный способ смешать руку и программу - читать руку через `0x54` и слать сумму; цена ~7.5 мс отставания на
  всём движении.
- Настройки платы (мёртвые зоны, кривые, strength) сейчас нулевые / линейные; влияют ли они на инжект - не измерено.

## 7. Нагрузка по COM и отказ USB3

Отказ: геймпад пропадает с платы (`0x02` = 0, `km.device()` = `R:-;M:0uf;K:0uf;C:0uf`, `0x54` = `FF`) и из Windows.
COM при этом жив. Предвестник (не всегда): секунды, где `sequence` растёт на ~900 вместо 1000.

| Нагрузка (кадров/с по COM) | 4126 | 4133 |
| --- | --- | --- |
| нет COM-трафика | 8-10 мин (радио), ~5 ч 50 мин (кабель) чисто | - |
| 100 чтений + 125 / 250 / 500 команд | по 180 с чисто (кабель) | - |
| 100 чтений + 500 команд с кнопками | 9 мин чисто (радио); на кабеле 2 отказа за 195 с | - |

| 2000 чтений, без команд (`repro_poll54`) | **5 из 5** за 4.3-108 с, порт мёртв до переподключения платы | 300 с чисто, 300 с чисто, отказ на 73-й с, встал за 1.4 с |

- MAKCU (2026-11-16): «500/с и 1000/с по 30 с безопасным пределом не считать». (2026-11-17): причина найдена, исправление в

- GameSir Connect, пока открыт, режет радио до ~225 отчётов/с. Геймпад по радио засыпает без касаний (~30 мин): в долгих
  прогонах владелец качает левый стик (`pad_probe_view --keepalive`).

## 8. Частота геймпада (125 / 250 / 500 / 1000 Гц)

Клон объявляет интервал настоящего геймпада, поэтому плата сама не отдаёт больше его частоты (слова владельца,
документация `CONTROLLER_PHYSICAL.md` им не противоречит). Отсюда ревизия 3 транспорта (§4.3) и 4 рендерера (§5).
Исключение - геймпад, который шлёт реже объявленного: инжект добавляет отчёты (225 -> ~722 пакета/с). Не проверено на
настоящем медленном геймпаде; GameSir владельца частоту опроса менять не умеет (Connect - только 8-кГц моделям).

## 9. COM-порт и синий экран

- Драйвер WCH `CH343S64.SYS` (2.1.2025.7 и 2.2.2026.5) падает с `0xD1` на разыменовании нуля внутри себя, в том числе при
  открытом молчащем порте. Первая версия этого транспорта (чтение с ожиданием первого байта до 2 мс) уронила Windows через
  ~12 тыс. запросов. **Правило: читать порт только без ожидания** (`ReadIntervalTimeout = MAXDWORD`, остальное 0), никаких
  тайм-аутов чтения. Этот транспорт так и сделан.
- **С 2026-11-16 COM5 на встроенном драйвере Windows `usbser.sys`**: 8 ч под нагрузкой без сбоя (на WCH та же нагрузка - синий
  экран за 8 мин). Проверка: `basics\comport_way\switch_ch343_driver.ps1 -Status` (служба должна быть `usbser`).
  Подробно: `HANDOFF_CH343_BSOD.md`.

## 10. Самопроверка

Перед любым живым прогоном: COM5 есть, Toolkit и GameSir Connect закрыты, `..\pad_probes\pad_probe_info.exe --poll 0` -
`kinds 82`, `km.device()` = `R:KC;M:0uf;K:64uf;C:8uf` (**`--poll 0` обязательно**: по умолчанию проба 2 с опрашивает без
паузы, ~3450/с). Рядом окно `..\pad_probes\pad_probe_view.exe --rate 0 --keepalive --dur S` (COM не занимает).

| Команда | Рука | Зачётно, если |
| --- | --- | --- |
| `example_pad.exe --check` | не нужна | «интервал 1000 мкс, отчётов ~1000/с», периоды 2000 / 2000 (Auto) или 1000 / 2000 (Off), `FF` 0 |
| `example_pad.exe` (круг 2 с) | не трогать правый стик | ~1000 команд (Auto) или ~2000 (Off), «стик отпущен нулями, подтверждение: да», починок 0 |
| `example_pad.exe --buttons 20` | жать кнопки и триггеры | каждое нажатие напечатано; задние кнопки = A / B |
| `pad_bench_com.exe --off --live ..\pad_probes\data\rec2 --from 17.5 --len 7` | не трогать | рендерер W1 ~3.5, запись руки ~1.2; иначе смотреть режим платы |
| `pad_soak.exe --steps all2-p500 --step 1200` | держать, качать левый стик | строка раз в 10 с; отказ - код 3 и строка `ОБРЫВ` |

## 12. Опровергнуто (не проверять заново)

- «Сетки АЦП у GameSir нет» - есть, ~101 единица в «сырых» координатах, её прячет калибровка.
- «Калибровка квадратичная `u * (1 + c r^2)`» и «усиление оси падает с отклонением другой» - нет, радиальная кривая отклика.
- «Обрывы геймпада от отпускания стика нулями» - 258 отпусканий за 180 с на 500 командах/с чисто.
- «Безопасно 500 команд/с» - на 4133 отказ и на 500 чтений + ~325 команд/с.
- «Плата при инжекте отдаёт больше отчётов, чем умеет геймпад» - только когда геймпад шлёт реже объявленного (Connect).

## 13. Протокол на проводе (справка)

Кадр `DE AD | LEN u16 LE | CMD | PAYLOAD`, COM5, 4 000 000 бод, DTR/RTS выключены. Ответ на ошибку - один байт `FF`.

| Команда | Тело запроса | Ответ |
| --- | --- | --- |
| `0x02` DEVICE | - | 1 байт `kinds` (`0x82` = клавиатура + XInput; геймпад = `kinds & 0xFC`) |
| `0x04` FIRMWARE | - | u32 LE (4133 = `25 10 00 00`) |
| `SET 0x40` CONTROLLER_STATE | 20 байт `<IIHHhhhh>`: кнопки low, high, LT, RT, LX, LY, RX, RY | - |
| `GET 0x40` | пусто | 20 байт заданного |
| `GET 0x54` CONTROLLER_PHYSICAL | пусто | 32 байта `<IIHHhhhhIIHH>`: те же 20 + `sequence`, `usb_timestamp` (x125 мкс), `timing` (dt в битах 0..13, baseline 14, invalid 15), `cadence` |
| `0x3E` [1D ...] | INFO 00, READ 01, BEGIN 02, WRITE 03, APPLY 04, SAVE 05 (не шлём), DISCARD 06 | см. `DEVICE_SETTINGS.md` |
| `0x73` / `0x74` | пусто - запрос; mode u8 (0 выкл, 1 текст, 2 двоичный) + period u16 мс | mode + period; события `0x75`: kind (1 оси, 2 кнопки), id, value u16; id 255 - снимок недоступен |

Образ настроек 400 байт: флаги u32 @0, интерполяция u32 @4 (0 Off, 1 Fixed, 2 Auto), буфер u32 @8, `behaviors[i]` с
20 + 88*i (правый стик i = 0).
